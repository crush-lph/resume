# 项目复盘口径模板

## 使用方法

把下面模板复制到每个项目下，填成自己的口述稿。面试时不要背全文，只记住关键结构和指标。

## 通用模板

### 1. 项目一句话介绍

这个项目是为谁服务、解决什么问题、业务价值是什么。

示例结构：

`这是一个面向 [用户群体] 的 [产品类型]，主要解决 [核心问题]，通过 [核心能力] 帮助用户实现 [业务结果]。`

### 2. 我的角色

说明你的职责边界。

可选角度：
- 是否负责前端架构。
- 是否参与技术选型。
- 是否负责核心模块。
- 是否带团队或做 Code Review。
- 是否协调产品、后端、测试、运营。

### 3. 核心难点

至少准备 2 到 3 个。

建议从这些维度选：
- 架构迁移难点。
- 性能瓶颈。
- 多端复用。
- 支付/权限/国际化等复杂业务。
- AI 流式输出或长任务状态管理。
- Chrome 插件多站点适配。
- 团队协作和质量保障。

### 4. 解决方案

每个难点按这个结构讲：

`问题是什么 -> 为什么难 -> 我做了什么 -> 如何验证有效`

不要只说“优化了”“封装了”“推动了”，要说清楚动作。

### 5. 结果与指标

每个指标都准备口径。

需要准备的指标：
- SEO 收录量：10W+ -> 500W+。
- FCP：0.8s -> 0.4s。
- LCP：20s -> 1.5s。
- 支付新渠道接入周期：约 0.5 天。
- 国际化交付周期：2 天 -> 0.5 天。
- TS any 占比：1% 以内。
- 编译错误率：下降 95%+。
- 小程序包体积：减少 35%。
- 冷启动速度：提升 30%。
- Webpack 构建时间：4 分钟 -> 1 分钟。
- 邮件编辑器加载性能：提升约 40%。

### 6. 复盘与改进

准备“如果再做一次会怎么做”。

可选方向：
- 更早建设指标监控。
- 更早统一类型和接口契约。
- 迁移前建立更细的兼容层。
- 对 AI 生成代码建立更严格的评审清单。
- 对组件库建立更明确的准入规则。

## FastMoss 数据平台口径

### 2 分钟介绍参考

FastMoss 是面向 TikTok 从业者的数据分析平台，主要解决商家选品、竞品调研和市场洞察等数据决策问题。我在项目中担任前端负责人，核心工作包括 Umi 到 Next.js 的 SSR 架构升级、SEO 和性能优化、支付与国际化能力建设，以及前端质量体系落地。

这个项目最有代表性的成果有三个。第一是通过 SSR、Blog 内容体系、动态元数据和内链结构优化，把 SEO 收录量从 10W+ 提升到 500W+。第二是基于 Lighthouse、Performance、Bundle Analyze 做性能治理，FCP 从 0.8s 优化到 0.4s，LCP 从 20s 优化到 1.5s。第三是统一支付和国际化能力，通过策略模式抽象不同支付渠道，新渠道接入周期缩短到约 0.5 天；通过 next-intl 和 Crowdin 将多语言交付周期从 2 天缩短到 0.5 天。

### 必备追问口径

- 为什么迁移：原 Umi 架构在 SEO、SSR、页面性能和后续扩展上存在限制，Next.js 更适合公开内容页、SEO 页面和多渲染模式并存的业务。
- 如何平滑迁移：按页面和业务模块拆分迁移范围，优先迁移 SEO 和性能收益明显的页面，保留旧项目稳定迭代，通过兼容层和统一规范降低迁移风险。
- SEO 为什么增长：技术侧解决可抓取、元数据、结构化内容和内链问题；内容侧通过 Blog 和数据页面扩大可收录规模。
- 性能怎么验证：上线前用 Lighthouse 和 Performance 做单页分析，上线后结合监控数据看真实用户指标变化。

## FastMoss 小程序口径

### 2 分钟介绍参考

FastMoss 小程序是 FastMoss 业务在小程序端的延伸，我主要负责前端架构、类型治理、性能优化和核心业务模块落地。这个项目的重点是多端复用、包体积控制、冷启动优化和团队协作效率提升。

我主导了 TypeScript 类型治理，将 any 占比压缩到 1% 以内，编译错误率下降 95%+，并完成 15+ 核心页面重构。同时推动 Monorepo 架构升级，复用 PC 与小程序公共逻辑，减少重复开发。性能方面，通过分包、懒加载和包体治理将包体积减少 35%，冷启动速度提升 30%；构建方面将 Webpack 构建时间从 4 分钟优化到约 1 分钟。

### 必备追问口径

- TS 治理：先统计 any 来源，再按接口响应、业务模型、组件 props、状态管理逐步收敛，不一次性大改阻塞业务。
- Monorepo：重点复用业务模型、工具函数、接口层、部分 Hooks，UI 层根据端差异保留适配。
- 小程序性能：优先处理包体积、首屏依赖、图片资源、非首屏模块加载。
- 构建优化：从缓存、loader、依赖分析、无效构建、并行处理等方向入手。

## ClawDream 口径

### 2 分钟介绍参考

ClawDream 是一款 AI 驱动的 Chrome 插件，用户上传头像后，可以结合目标站点的图片、视频等内容生成数字人形象，实现一键试穿或风格预览。我在项目中负责前端架构和核心模块落地，包括插件架构、数据采集、消息通信、状态反馈、Firebase 登录和 Chrome Store 上架。

技术上，项目基于 Plasmo 开发，通过 Content Script 在目标站点采集数据，封装成标准化协议后，经消息通道发送到 Background 处理，从而解耦页面环境和插件核心逻辑。研发方式上，我深入实践 Vibe Coding，使用 Claude Code 结合 MCP、Skills 完成需求拆解、方案实现、单元测试、文档生成和联调排查等环节，提高开发效率。

### 必备追问口径

- 插件架构：Content Script 负责页面注入和采集，Background 负责核心逻辑、状态协调和跨页面任务处理。
- 解耦原因：目标站点 DOM 和运行环境不可控，核心逻辑需要稳定、可测试、可复用。
- 标准化协议：把不同站点采集到的数据统一成业务可处理的结构，降低后续适配成本。
- AI 辅助研发：不是让 AI 直接替代开发，而是把 AI 放进需求拆解、初稿实现、测试补充、文档生成和问题排查流程，最后通过人工评审保证质量。

## Oumomo 口径

### 1 分钟介绍参考

Oumomo 是面向 TikTok 卖家的 AI 带货视频创作平台，覆盖脚本、画面、配音到发布的创作链路。我主要负责前端工程搭建、技术选型和基础能力建设，包括目录结构、工程规范、国际化、支付、授权登录、落地页动效和首屏加载优化。

### 必备追问口径

- 工程搭建：先确定目录规范、组件组织、状态管理、请求封装、权限、国际化和样式方案。
- 动效优化：只对关键视觉路径使用动效，非首屏模块动态加载，避免影响首屏性能。
- AIGC 链路：重点关注长任务状态、进度反馈、失败重试和结果回显。

## MossCreator 口径

### 2 分钟介绍参考

MossCreator 是面向 TikTok 商家的达人营销管理工具，帮助商家完成达人匹配、批量建联、AI 内容生成、流程跟踪和团队管理。我负责前端从 0 到 1 搭建，包括技术选型、工程架构、登录、达人广场、批量邮件、支付、会员权限、团队管理和海外本地化等核心流程。

项目中比较有代表性的难点是邮件编辑器和邀约跟踪流程。我定制开发了邮件编辑器和任务邀约跟踪能力，并通过懒加载、CDN 等方式将编辑器加载性能提升约 40%。同时实现接口签名、代码混淆等安全策略，并基于 SSE 实现 AI 内容流式生成和多时区定时发布。

### 必备追问口径

- 邮件编辑器：复杂点在富文本编辑、模板变量、商品卡片、邀约状态和性能加载。
- 安全策略：接口签名防止请求被篡改，代码混淆提高逆向成本，但不能替代服务端安全。
- 多时区：前端负责选择和展示，存储和执行应以统一时间基准交给服务端处理。
