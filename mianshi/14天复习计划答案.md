## 第 2 天：FastMoss 数据平台项目复盘

### 2 分钟项目介绍

FastMoss 是面向 TikTok 从业者的数据分析平台，核心用户包括跨境商家、达人机构和运营人员，主要解决选品、竞品调研、达人分析和市场洞察问题。我在项目中担任前端负责人，负责 Umi 到 Next.js 的架构升级、SSR 与 SEO 优化、首屏性能治理、支付与国际化能力建设，以及团队质量规范。

这个项目最重要的技术动作是架构迁移。原来的 Umi SPA 对公开内容页和 SEO 支持有限，首屏依赖客户端渲染，搜索引擎抓取和页面性能都有瓶颈。所以我们引入 Next.js，把 SEO 页面、Blog、数据公开页逐步迁移到 SSR/SSG/ISR 更合适的渲染模式。

迁移过程中没有暂停业务迭代，而是按页面和业务模块拆分，优先迁移 SEO 和性能收益高的页面；旧项目继续承接存量业务，新项目承接新增和改造模块；公共请求、权限、埋点、组件和样式规范尽量统一，减少两套体系带来的维护成本。最终通过 SSR、动态元数据、结构化内容、内链和 sitemap 等能力，把 SEO 收录从 10W+ 提升到 500W+；通过 Lighthouse、Performance、Bundle Analyze 做性能治理，FCP 从 0.8s 到 0.4s，LCP 从 20s 到 1.5s。

### Umi -> Next.js 迁移追问

**为什么迁移 Next.js？**

核心原因是业务进入增长阶段后，SEO、首屏性能和多渲染模式变得非常重要。Umi 更适合中后台和 SPA 业务，但对大规模公开页、动态 meta、SSR/SSG/ISR 混合场景不是最优。Next.js 可以按页面选择 CSR、SSR、SSG、ISR，更适合数据平台中“公开 SEO 页面 + 登录后复杂应用”并存的形态。

**怎么做到不暂停业务迭代？**

采用渐进式迁移：先按业务价值划分迁移边界，优先迁移 Blog、公开数据页、落地页等 SEO 收益明显的页面；旧 Umi 项目继续维护存量后台和低优先级模块；公共层面统一接口封装、权限判断、埋点、样式变量和组件规范；每个迁移页面都有灰度、回滚和指标对比。

**迁移后收益如何验证？**

性能看 Lighthouse、Performance 和线上真实用户指标，重点关注 FCP、LCP、JS 体积、接口耗时。SEO 看 Google Search Console 或站长平台中的收录量、曝光、点击和索引状态。业务上看自然流量、注册转化、支付转化等后续指标，避免只看收录量。

## 第 3 天：Next.js / SSR / SEO

### SEO 优化路径图

```txt
页面可抓取
  -> SSR / SSG / ISR 输出稳定 HTML
  -> 动态 title、description、canonical
  -> 结构化内容和语义化标签
  -> Blog / 数据页扩大内容规模
  -> 内链体系提升页面发现效率
  -> sitemap / robots 引导爬虫
  -> Search Console 监控收录、曝光、点击
  -> 转化数据验证业务价值
```

### SEO 指标口径

SEO 收录从 10W+ 到 500W+，口径应该说明数据来源、统计周期和页面范围。面试中可以说：这个指标主要看 Google Search Console 或站长平台中有效索引页面数，统计范围是 FastMoss 公开可访问页面，包括 Blog、数据详情页、榜单页等，不包含登录后不可访问页面。除了收录量，还会结合曝光、点击、自然搜索流量和注册转化看真实价值。

### 自测答案

**SSR 为什么有利于 SEO？**

SSR 能在服务端直接输出包含核心内容的 HTML，爬虫不需要等待客户端 JS 执行才能看到页面主体内容。它解决的是可抓取性和首屏内容稳定性问题。但 SSR 不是 SEO 的全部，还要配合 meta、canonical、结构化数据、内容质量、内链和 sitemap。

**动态元数据怎么做？**

按页面数据生成 title、description、keywords、canonical、Open Graph 等信息。Next.js 中可以在服务端数据获取阶段或 metadata API 中生成。关键是保证元数据和页面主体内容一致，避免大量重复标题、空描述或低质量聚合页。

**多语言页面 SEO 怎么处理？**

需要稳定 URL 结构，比如 `/en/xxx`、`/zh/xxx`；使用 `hreflang` 告诉搜索引擎不同语言版本的对应关系；每个语言页面生成对应语言的 title、description 和 canonical；sitemap 中也要覆盖多语言地址。日期、货币、时区也要按 locale 展示。

## 第 4 天：性能优化

### 性能优化排查 checklist

- 指标定义：明确 FCP、LCP、TTFB、CLS、INP 分别异常在哪里。
- 网络层：检查 TTFB、接口耗时、CDN、缓存、资源压缩。
- 资源层：检查图片、字体、第三方脚本、首屏 CSS/JS 体积。
- JS 层：用 Bundle Analyze 查大依赖，用 Performance 查长任务。
- 渲染层：检查大 DOM、图表渲染、同步计算、布局抖动。
- 框架层：检查 dynamic import、路由级拆包、SSR/CSR 边界。
- 验证层：上线前实验室指标，上线后真实用户指标持续监控。

### 标准答案：我如何做性能优化

我做性能优化一般不会先猜方案，而是先明确指标和场景。比如 FastMoss 当时关注 FCP 和 LCP，我先用 Lighthouse 看整体评分和机会项，再用 Performance 面板看主线程、网络瀑布流和渲染阻塞，最后用 Bundle Analyze 找大包和不合理依赖。

针对首屏，我会优先处理几类问题：服务端响应和接口是否慢，首屏 JS 是否过大，图片和字体是否阻塞，第三方脚本是否影响主线程，图表或表格是否在首屏同步渲染。具体方案包括 SSR/SSG 改造、首屏数据预取、图片压缩和尺寸声明、字体加载策略、dynamic import、路由拆包、延迟加载非首屏模块，以及缓存和 CDN 优化。最终用同一测试环境和线上真实用户指标验证，避免只在本地感觉变快。

### 自测答案

**LCP 20s 的可能原因有哪些？**

可能是服务端 TTFB 太高、首屏接口慢、LCP 元素是大图且没有优化、JS 包太大导致 hydration 阻塞、第三方脚本占用主线程、图表/表格同步计算太重、资源没有走 CDN 或缓存策略错误。

**如何区分网络、资源、JS、渲染、接口瓶颈？**

看 Network 瀑布流判断 TTFB、接口和资源下载；看 Performance 的 Main Thread 判断 JS 长任务和渲染阻塞；看 Bundle Analyze 判断包体；看 Lighthouse 的 LCP 元素定位具体首屏元素；必要时加前端埋点拆分 DNS、TCP、TTFB、下载、渲染和接口耗时。

**性能优化如何持续监控？**

上线后接入 RUM 指标，持续采集 FCP、LCP、CLS、INP、接口耗时、错误率，并按页面、地区、设备和网络分组。关键页面设置阈值告警，发版后对比指标趋势，避免一次优化后又回退。

## 第 5 天：支付、国际化、权限

### 支付渠道抽象设计

前端不负责最终资金安全，但负责用户支付链路体验、渠道 SDK 调起、订单状态展示、异常兜底和状态同步。策略模式可以把不同渠道差异封装成统一接口：

```ts
interface PaymentStrategy {
  createOrder(params: CreateOrderParams): Promise<Order>;
  pay(order: Order): Promise<void>;
  queryStatus(orderId: string): Promise<PaymentStatus>;
  cancel?(orderId: string): Promise<void>;
}
```

业务层只关心“创建订单、发起支付、查询状态、处理结果”，微信、支付宝、Stripe、PayPal、Airwallex 的差异放在各自策略里。新渠道接入快，是因为订单页、状态轮询、异常提示、埋点和结果页都复用，只新增渠道策略和少量配置。

### 国际化流程说明

next-intl 负责运行时语言加载、路由 locale、变量插值和日期货币格式化；Crowdin 负责翻译协作、文案提交、翻译、审核和同步。流程是：开发提取 key -> 上传 Crowdin -> 翻译/审核 -> 同步语言包 -> 预发验收 -> 发布。交付周期从 2 天到 0.5 天，缩短的是人工复制、沟通确认、重复翻译和回填语言包的时间。

### 权限方案说明

浏览次数限额权限可以拆成三层：前端展示层负责按钮、弹窗、剩余次数提示；接口层负责每次访问时返回权限状态和剩余额度；后端负责真正扣减、校验和防刷。前端不能只靠本地状态限制，否则容易被绕过。体验上要在用户触达限制前提前提示，并提供升级入口。

### 自测答案

**新支付渠道为什么能 0.5 天接入？**

因为提前抽象了统一支付接口和状态机。新增渠道时主要补渠道策略、SDK 配置、渠道参数映射和少量异常码处理，订单创建、结果页、轮询、埋点、灰度和 UI 流程都复用。

**支付异常和状态同步怎么处理？**

不能只相信前端回调。前端回调后要查询服务端订单状态；如果用户关闭页面或 SDK 没回调，要用轮询、结果页主动查询或用户返回后恢复状态。异常包括取消、超时、重复支付、订单过期、汇率变化等，都要有明确提示和重试/重新下单入口。

**多语言交付周期为什么能缩短？**

因为文案从“人工散落维护”变成“key + 平台协作 + 自动同步”。翻译人员在 Crowdin 里处理，开发不用反复复制粘贴；next-intl 统一加载和格式化，减少页面适配成本。

## 第 6 天：FastMoss Agent 与 SSE

### SSE 选型说明

FastMoss Agent 主要是用户发起问题后，服务端持续返回模型生成内容，本质是服务端到客户端的单向文本流。SSE 基于 HTTP，适合文本流，接入成本低，和现有鉴权、网关、日志、监控体系兼容更自然。WebSocket 适合双向高频实时通信，比如协同编辑或游戏，但在 AI 文本生成场景中连接管理、心跳和协议治理成本更高。

### 长对话性能优化说明

流式输出不能每来一个 token 就 setState。更稳的做法是把 token 写入 ref 缓冲区，再按 `requestAnimationFrame` 或固定时间片批量刷新，只更新当前最后一条 assistant 消息。历史消息保持稳定，长列表使用虚拟列表；Markdown、代码高亮、公式和自动滚动做节流或分阶段处理。对已完成消息缓存渲染结果，避免滚动时重复解析 Markdown。

### 自测答案

**为什么用 SSE？**

因为 AI 生成是典型的单向流式输出，SSE 简单、HTTP 友好、适合文本增量返回。只有当业务需要客户端和服务端双向高频通信时，我才会优先考虑 WebSocket。

**流式输出如何避免频繁渲染？**

用缓冲区聚合 token，按帧或按时间片提交到 React state；只更新当前生成消息；历史消息组件 memo 化；长对话用虚拟列表；自动滚动和 Markdown 渲染节流。

**Markdown 渲染如何做安全防护？**

模型输出不能直接当 HTML 注入。默认关闭原始 HTML，或使用 DOMPurify 白名单清洗；链接、图片、代码块要做协议和属性过滤；代码高亮只处理文本，不执行脚本；后端也要对敏感内容和工具调用结果做校验。

## 第 8 天：FastMoss 小程序

### 2 分钟项目介绍

FastMoss 小程序是 FastMoss 业务在移动端和微信生态内的延伸，主要承接数据查询、会员权益、分享裂变和核心业务触达。我主要负责前端架构、类型治理、Monorepo 升级、核心页面重构和性能构建优化。

这个项目的难点在于小程序有包体限制、运行环境和 Web 不同，同时业务又希望和 PC 复用部分数据模型、接口逻辑和工具方法。我推动了 TypeScript 治理，把 any 占比压到 1% 以内，编译错误率下降 95%+；推动 Monorepo 架构，复用接口层、业务模型、工具函数和部分 Hooks；性能上通过分包、懒加载、图片压缩和首屏依赖治理让包体积减少 35%、冷启动提升 30%；构建上通过缓存、loader 优化和依赖分析，把 Webpack 构建时间从 4 分钟降到约 1 分钟。

### TS 治理方法论

先统计 any 来源，区分接口响应、业务模型、组件 props、状态管理和临时绕过。治理时不一次性大改，而是先建立核心类型和接口响应泛型，再按高频模块逐步替换 any；新增代码通过 ESLint 和 Code Review 限制 any 扩散；对复杂动态数据用 unknown + 类型守卫，而不是继续 any。

### Webpack 构建优化说明

先分析构建耗时分布，看是 loader 慢、依赖重复、缓存失效还是产物过大。常见动作包括开启持久化缓存、缩小 loader include 范围、优化 babel/ts 编译、合理使用 thread-loader、减少无效 polyfill、拆分公共依赖、避免重复编译。优化后用统一机器和同一命令对比冷构建与热构建耗时。

### 自测答案

**any 占比怎么统计？**

可以用 ESLint 规则、ts-morph 或脚本扫描统计 `any` 显式使用数量，再除以类型声明或 TS 文件整体规模。更重要的是按模块和来源分类，区分临时绕过、第三方类型缺失、接口未建模和组件 props 泛化。

**Monorepo 复用了哪些逻辑？**

主要复用业务模型、接口请求封装、常量、工具函数、权限判断、埋点方法和部分无 UI 依赖的 Hooks。UI 层和平台能力要保留适配，因为小程序和 Web 的组件、路由、生命周期不同。

**构建时间为什么能降到 1 分钟？**

不是单点优化，而是缓存、loader 范围、依赖体积、并行处理和无效构建一起治理。尤其是持久化缓存和缩小编译范围，对重复构建收益明显。

## 第 9 天：组件抽象与业务增长

### 组件抽象边界说明

组件抽象不是看到重复代码就封装，而是看变化点是否稳定、调用场景是否足够多、业务规则是否能抽离。通用组件关注 UI 行为和数据协议，比如 VirtualList、Table、Cascader；业务组件可以绑定具体场景，比如会员弹窗、支付卡片、分享裂变组件。边界不清时，宁可先做局部复用，不要过早做大而全的组件。

### 如何判断组件该不该抽象

我会看四点：第一，是否至少在多个稳定场景重复出现；第二，重复的是结构和行为，还是只是样式相似；第三，未来变化点是否可预测；第四，抽象后是否降低维护成本。如果抽象需要暴露大量配置才能满足业务，说明边界可能不稳定，应该先沉淀业务组件或 Hook。

### 自测答案

**VirtualList 原理是什么？**

虚拟列表的核心是只渲染可视区域附近的元素。通过容器滚动位置计算 startIndex 和 endIndex，用占位高度撑开滚动条，再把可见元素定位到对应位置。固定高度比较简单，动态高度需要缓存每项高度并在测量后修正偏移。

**通用组件和业务组件如何区分？**

通用组件不关心具体业务，只暴露数据、事件和展示能力；业务组件可以包含业务状态、权限、埋点和接口逻辑。比如 Table 是通用组件，会员套餐表格或支付订单表是业务组件。

**如何避免过度封装？**

不为了“看起来复用”而封装。抽象前先确认稳定重复，抽象后控制 API 数量；复杂业务优先组合而不是继承式配置；组件库要有准入标准、文档、示例和维护人。

## 第 10 天：ClawDream Chrome 插件

### 2 分钟项目介绍

ClawDream 是一款 AI 驱动的 Chrome 插件，用户可以基于目标站点的图片、视频或商品内容，结合自己的素材生成数字人试穿或风格预览。我负责插件前端架构和核心模块，包括 Plasmo 工程、Manifest V3、Content Script 数据采集、Background 状态协调、消息通信、Firebase 登录、任务状态反馈、调试面板和 Chrome Store 上架。

技术上，目标站点环境不可控，所以我把页面采集和核心业务逻辑解耦。Content Script 负责读取页面 DOM、提取图片/视频/商品信息，并转成统一标准化协议；Background 负责跨页面状态、任务调度、鉴权和接口交互；Popup 或 Side Panel 负责用户操作和进度反馈。多站点适配时，站点差异被隔离在 adapter 中，核心流程只消费统一数据结构。

研发方式上，我把 AI 工具纳入流程，而不是让 AI 直接生成后合入。Claude Code 负责需求拆解、初稿实现和排查建议，MCP 帮助连接上下文和工具，Skills 固化项目规范、测试和文档要求。最终代码仍通过人工 Review、类型检查、单测和联调验证。

### 插件架构图

```txt
目标网页
  -> Content Script：DOM 采集、页面注入、站点 adapter
  -> Message Channel：统一消息协议、超时、错误码
  -> Background Service Worker：鉴权、任务调度、接口请求、状态缓存
  -> Popup / Side Panel：用户操作、进度反馈、结果展示
  -> 后端 / AI 服务：识别、生成、任务结果
```

### 自测答案

**Content Script 和 Background 如何通信？**

通过 `chrome.runtime.sendMessage` 或长连接 `connect` 通信。短任务用 sendMessage，持续任务或状态订阅可以用 Port。消息需要统一 type、payload、requestId、timeout 和 error，避免异步响应丢失。

**多站点差异怎么适配？**

每个站点实现独立 adapter，负责 DOM 选择器、字段提取和兼容逻辑，输出统一数据协议。核心业务不直接依赖某个站点 DOM，这样新增 Instagram、Amazon、Pinterest、Etsy 时只扩展 adapter。

**如何保证 AI 生成代码质量？**

AI 只进入需求拆解、方案初稿、测试补充和排查建议环节，合入前必须过类型检查、lint、单测、人工 Review 和真实场景联调。重点审查安全边界、异常处理、状态一致性、可维护性和是否符合项目规范。

## 第 11 天：Oumomo 与 MossCreator

### Oumomo 1 分钟介绍

Oumomo 是面向 TikTok 卖家的 AI 带货视频创作平台，覆盖脚本生成、素材选择、配音、视频生成和发布链路。我主要负责前端从 0 到 1 搭建，包括技术选型、目录规范、组件体系、国际化、支付、授权登录、落地页动效和首屏加载优化。技术上使用现代 React 生态、shadcn/ui、Tailwind 和 motion，但会控制动效范围，非首屏模块用 dynamic import 延迟加载，避免视觉效果影响首屏性能。

### MossCreator 2 分钟介绍

MossCreator 是面向 TikTok 商家的达人建联和营销管理平台，帮助商家完成达人筛选、批量邀约、邮件触达、AI 内容生成、邀约状态跟踪和团队管理。我负责前端从 0 到 1 搭建，包括技术选型、工程规范、登录、达人广场、批量邮件、支付、会员权限、团队管理和海外本地化。

项目里比较复杂的是邮件编辑器和邀约跟踪流程。邮件编辑器涉及富文本、模板变量、商品卡片、达人信息、预览、发送状态和性能加载，我通过懒加载、CDN 和编辑器初始化优化，让加载性能提升约 40%。安全上实现接口签名和代码混淆，接口签名降低请求被篡改风险，代码混淆提高逆向成本，但最终安全仍依赖服务端校验。AI 内容生成部分使用 SSE 做流式输出，并支持多时区定时发布，前端负责时间选择、展示和转换，服务端按统一时间基准执行。

### 邮件编辑器性能优化说明

邮件编辑器慢通常来自编辑器包体大、插件多、模板资源多、初始化同步任务重。优化方式是动态加载编辑器、按需加载插件、模板和素材懒加载、静态资源走 CDN、缓存常用模板、减少初始化时的同步计算，并把预览和编辑态拆开。验证口径可以用编辑器首屏可交互时间或初始化完成时间。

### 自测答案

**邮件编辑器复杂在哪里？**

复杂在它不是普通富文本，还要支持模板变量、商品/达人信息插入、预览、批量发送、状态跟踪、多语言和不同邮箱客户端兼容。

**接口签名和代码混淆解决什么问题？**

接口签名用于校验请求参数、时间戳和身份，降低请求被篡改、重放的风险；代码混淆提高逆向成本。但二者都不能替代服务端鉴权、权限校验和风控。

**多时区定时发布怎么做？**

前端展示用户本地时区和目标时区，提交时把时间和时区信息传给服务端，服务端转换为统一时间基准存储和执行。回显时再按用户 locale 和时区格式化，避免夏令时和跨时区误差。

## 第 12 天：工程化与团队管理

### Code Review 标准清单

- 功能正确：是否覆盖核心流程、边界和异常。
- 类型安全：是否有 any 扩散，接口类型是否准确。
- 性能影响：是否引入大包、重复渲染、阻塞首屏。
- 安全边界：XSS、权限、支付、接口签名、敏感信息是否处理。
- 可维护性：命名、拆分、复用边界是否清楚。
- 用户体验：loading、empty、error、retry、弱网是否完整。
- 测试验证：是否有必要的单测、联调记录或自测说明。

### 团队管理案例

**案例 1：推动规范落地**

我不会只发一份规范要求大家遵守，而是把规范接入工具链。ESLint、Prettier、Husky 负责提交前拦截，CI 负责合并前检查，Code Review 清单负责人工判断复杂问题。新项目先用模板和示例降低接入成本，存量项目按模块逐步治理，避免一次性大改影响业务。

**案例 2：7 人团队任务分配**

我会按业务线和技术能力拆分 owner，比如核心交易链路、数据页面、组件库、小程序、AI 模块分别有人负责。需求进入后先明确优先级、风险和依赖，再拆成可交付任务；关键方案先评审，开发中同步风险，合并前做 Review 和测试验收。

### 技术方案推动案例

以 Umi 迁移 Next.js 为例，我先明确业务目标是 SEO 增长和性能优化，再用数据说明原架构瓶颈；方案上选择渐进迁移，降低业务中断风险；过程中先做收益高的页面验证效果，再沉淀公共层和规范，最后用 SEO、FCP、LCP 和线上指标证明收益。

### 自测答案

**如何推动规范落地？**

规范必须工具化、流程化和示例化。工具化靠 lint、format、commit hook、CI；流程化靠 Review 清单和准入规则；示例化靠模板、文档和新人培训。

**如何判断技术债是否该处理？**

看它是否影响业务交付、线上稳定性、性能、安全或团队效率。如果只是代码不够优雅但风险低，可以等业务窗口；如果已经导致线上问题、开发频繁踩坑或阻碍关键需求，就应该排期治理。

**如何协调多部门需求优先级？**

先把需求翻译成业务目标、收益、风险和成本，再和产品、运营、后端一起确认优先级。对冲突需求给出方案选项和影响范围，而不是只说做不了。

## 第 13 天：基础查漏补缺

### 20 个基础题速答卡

1. React 渲染流程：setState 触发更新，调度后进入 render 协调 Fiber 树，commit 阶段提交 DOM 变更。
2. Fiber 作用：把渲染工作拆成可调度工作单元，支持中断、恢复和优先级。
3. key 作用：帮助 React 识别同层节点身份，减少错误复用和不必要重建。
4. useEffect vs useLayoutEffect：前者在浏览器绘制后执行，后者在 DOM 更新后、绘制前同步执行。
5. useMemo：缓存计算结果，不保证一定提升性能，适合昂贵计算或稳定引用。
6. useCallback：缓存函数引用，常用于传给 memo 子组件或 effect 依赖。
7. 重复渲染定位：React DevTools Profiler、why-did-you-render、Performance 面板。
8. Zustand vs Redux：Zustand 轻量直接，Redux 更适合复杂可追踪状态和大型协作。
9. CSR：客户端渲染，适合登录后强交互页面。
10. SSR：服务端每次请求渲染，适合动态 SEO 页面。
11. SSG：构建时生成静态页，适合内容稳定页面。
12. ISR：静态页按时间或事件增量更新，适合大量半动态内容。
13. Hydration mismatch：服务端 HTML 和客户端首次渲染不一致，常见于时间、随机数、环境判断。
14. any vs unknown：any 放弃类型检查，unknown 需要收窄后使用。
15. never：表示不会出现的类型，常用于穷尽检查。
16. 泛型：把类型作为参数，提高复用和类型安全。
17. 条件类型：根据类型关系生成不同类型，适合工具类型。
18. 事件循环：同步任务先执行，宏任务结束后清空微任务，再进入渲染和下一个宏任务。
19. Tree Shaking：基于 ESM 静态分析移除未使用代码，副作用或 CJS 可能导致失效。
20. Source Map：把压缩后的代码映射回源码，方便调试和错误定位。

### 5 个容易卡住的问题

**React 如何定位重复渲染？**

先用 Profiler 看哪些组件渲染频繁和耗时高，再检查 props 是否每次创建新引用、状态是否放得过高、Context 是否导致大范围更新、memo 是否被不稳定函数或对象破坏。

**Tree Shaking 为什么会失效？**

常见原因是使用 CommonJS、模块有副作用、`sideEffects` 配置不准确、动态导入路径无法静态分析、整体引入大库而不是按需引入。

**浏览器从输入 URL 到页面展示发生了什么？**

DNS 解析、建立 TCP/TLS、发送 HTTP 请求、服务端响应 HTML、浏览器解析 HTML 构建 DOM、解析 CSS 构建 CSSOM、加载 JS 和资源、生成渲染树、布局、绘制、合成，期间 JS 可能阻塞解析或触发重新渲染。

**Promise.then 和 setTimeout 顺序？**

同步代码先执行，Promise.then 进入微任务，setTimeout 进入宏任务；当前宏任务结束后先清空微任务，所以 Promise.then 先执行。

**前端缓存策略怎么设计？**

HTML 通常不强缓存或短缓存，确保发版更新；带 hash 的 JS/CSS 可以长期强缓存；接口缓存按业务实时性决定；图片和字体走 CDN 和强缓存；需要配合版本号、ETag、Cache-Control 和 Service Worker 策略。
