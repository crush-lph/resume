## 1. 项目底层的难点挖掘（支付服务 / Next 服务端客户端通信）

### 关键考点

- 你是否能把“难点”讲成业务复杂度，而不是代码细节堆砌。
- 你是否理解支付链路和 SSR/CSR 通信链路的根本矛盾。
- 你是否有抽象和收敛复杂度的能力。

### 短答

我会把项目底层难点拆成两类：支付服务的状态一致性问题，以及 Next.js 里服务端和客户端通信的上下文一致性问题。

### 详细分析

**支付服务的难点**

支付的核心难点不是接几个 SDK，而是状态一致性。因为支付链路通常同时涉及：

- 外部支付渠道回调
- 前端页面状态
- 服务端订单状态
- 用户权益刷新

这些状态是异步的，所以容易出现：

- 已支付但前端没感知
- 支付成功但权益没刷新
- 回调丢失或用户中途关闭页面

解决思路通常是：

- 用策略模式封装多渠道差异
- 统一订单创建、支付发起、状态查询接口
- 以前端轮询服务端订单状态作为状态收敛手段
- 支付成功后统一刷新用户信息和权益

**Next 服务端和客户端通信的难点**

这部分本质是 SSR/CSR 上下文不一致。常见问题有：

- 服务端和客户端拿到的 cookie/header 不同
- 服务端能访问请求头，客户端不能
- 同一个页面在服务端首屏和客户端 hydration 阶段上下文不一致
- 用户态、地区、语言、来源信息需要跨运行时透传

解决思路通常是：

- 设计 SSR/CSR 一体化请求层
- 统一封装 cookie/header/region/lang/source 的透传逻辑
- 服务端渲染只做首屏确定性输出
- 浏览器环境相关逻辑放到 `useEffect`

### 可背答案

> 如果让我讲项目底层难点，我会重点讲两类。第一类是支付服务的状态一致性问题，因为支付不是单点流程，而是外部渠道、前端页面、服务端订单和用户权益四方异步协同，很容易出现已支付未生效、回调丢失、状态不同步的问题。所以我会通过统一支付抽象、订单轮询和用户态刷新来收敛状态。  
>   
> 第二类是 Next.js 里服务端和客户端通信的上下文一致性问题。SSR 和 CSR 运行环境不同，cookie、header、地区、语言、来源这些信息如果不统一透传，就容易出现服务端首屏和客户端状态不一致。我通常会通过 SSR/CSR 一体化请求层和上下文透传机制，把这些差异收敛掉。

### 注意点

- 不要把“难点”讲成“我写了很多代码”。
- 支付题一定要强调最终状态以后端订单为准。
- Next 通信题一定要落到“上下文一致性”上，而不是只说接口请求。

### 可能追问

- 支付为什么不能只相信前端回调？
- Next 服务端和客户端最大的差异是什么？
- 如果服务端和客户端拿到的用户态不一致怎么处理？

## 2. Vibe Coding 最佳实践

### 关键考点

- 你是否把 AI 当成工程能力，而不只是补全工具。
- 你是否知道大型项目里 AI 的风险边界。
- 你是否有 Prompt / Skill / Checklist 的沉淀意识。

### 短答

Vibe Coding 最佳实践的重点不是“让 AI 多写代码”，而是让 AI 进入一套有约束、有模板、有质量门禁的研发流程。

### 详细分析

最佳实践通常分四层：

**第一层：明确适合 AI 的任务**

- 样板代码
- 类型补全
- 单测草稿
- 文档和 PR 描述
- Bug 排查和影响面分析

**第二层：先有规范，再让 AI 参与**

- 目录结构
- 模块边界
- 请求层规范
- 组件规范
- 状态管理规范

没有这些约束，AI 会输出不稳定代码。

**第三层：资产沉淀**

- Prompt 模板
- 项目专属 Skill
- Code Review Checklist
- 常用代码模板

**第四层：质量门禁**

- TypeScript
- ESLint
- 单测 / E2E
- 构建检查
- 人工 Review

### 可背答案

> 我理解 Vibe Coding 的最佳实践，不是让 AI 替代工程师写代码，而是让 AI 进入一套稳定的工程流程。首先要明确哪些任务适合 AI，比如样板代码、类型补全、测试草稿、文档和排查；其次要先把项目的目录结构、模块边界、组件和请求层规范定下来；然后把高频任务沉淀成 Prompt、Skill 和 Checklist；最后仍然通过类型、Lint、测试、构建和人工 Review 做质量门禁。  
>   
> 所以 Vibe Coding 真正的价值不是“写得快”，而是把团队经验转成可复用资产，在不牺牲质量的前提下提升交付效率。

### 注意点

- 不要把 AI 讲成自动写完整项目。
- 不要忽略一致性和质量门禁。
- 最好强调核心链路要更保守，比如支付、权限、登录、SSR。

## 3. Zustand 的底层原理

### 关键考点

- 你是否知道 Zustand 不是魔法，而是“外部 store + 发布订阅”。
- 你是否理解它和 Redux / Context 的核心差异。
- 你是否知道 React 是怎么订阅它的。

### 短答

Zustand 的底层本质是一个独立于 React 之外的 store，加上一套发布订阅机制，组件通过订阅 store 的变化触发更新。

### 详细分析

Zustand 的核心思路很简单：

1. 在外部维护一个状态对象。
2. 提供 `getState`、`setState`、`subscribe`。
3. 组件通过 Hook 读取选中的状态切片。
4. 当 store 更新时，通过订阅通知组件重新取值。

它和 Context 的区别：

- Context 更像依赖 React 树传递值。
- Zustand 的 store 独立于组件树，更新不需要从 Provider 顶层往下扩散。

它和 Redux 的区别：

- Zustand 更轻，没有强制 reducer/action 模式。
- Redux 更强调严格数据流和中大型状态治理。

### 可背答案

> Zustand 的底层本质上是一个独立于 React 之外的外部 store，再加上发布订阅机制。它会维护一份状态对象，并暴露 `getState`、`setState` 和 `subscribe` 这类能力。组件通过 Hook 订阅自己关心的状态切片，store 更新后只通知相关订阅者重新取值，所以它比单纯用 Context 更灵活，也更容易避免全树级联更新。  
>   
> 我理解 Zustand 的核心价值是轻量、直观、适合做用户态、权限态、支付态这类跨页面共享的客户端状态。

### 注意点

- 不要把 Zustand 说成“基于 Proxy”，那是另一类状态库思路。
- 它不是自动解决接口缓存的，服务端状态仍然建议交给 React Query / SWR。

### 可能追问

- Zustand 为什么通常比 Context 更新开销更可控？
- Zustand 适合什么状态，不适合什么状态？
- 它怎么避免无关组件都更新？

## 4. 性能优化

### 关键考点

- 你是否有系统的性能排查顺序。
- 你是否能区分首屏、交互、渲染、网络、构建性能。
- 你是否能讲“定位 -> 方案 -> 结果”。

### 短答

性能优化我会先分场景：首屏性能、交互性能、渲染性能和资源加载性能，然后按瓶颈逐层排查。

### 详细分析

常见排查顺序：

1. 看是服务端慢、接口慢还是前端渲染慢。
2. 看首屏资源体积、JS 包大小、图片和字体。
3. 看是否有大列表、重计算、重复渲染。
4. 看第三方脚本是否阻塞主线程。
5. 上线后用 RUM 指标持续回看。

常见优化动作：

- 拆包、懒加载、动态加载
- SSR / SSG / ISR
- 图片压缩和尺寸声明
- 字体优化
- 列表虚拟化
- memo / useMemo / useCallback
- Web Worker

### 可背答案

> 性能优化我不会一上来就套方案，而是先定位瓶颈。通常会先区分是服务端响应慢、接口慢、资源太大、JS 执行太重，还是渲染阻塞。然后针对性处理，比如首屏用 SSR、拆包、懒加载、图片和字体优化；交互卡顿看重复渲染、大列表和重计算；长任务可以考虑节流、拆分和 Worker。  
>   
> 我比较看重的是“同一测试口径下验证结果”，比如 FCP、LCP、INP 和线上 RUM 数据，而不是只说页面感觉变快了。

### 注意点

- 不要把性能优化全讲成前端包体问题。
- 最好强调“先定位，再优化，再验证”。

### 可能追问

- 你怎么判断是接口慢还是渲染慢？

## 6. React 渲染流程，同步还是异步

### 关键考点

- 你是否区分 render 阶段和 commit 阶段。
- 你是否知道 React 18 里为什么不能简单说同步或异步。

### 短答

React 渲染不能简单说成同步或异步。更准确地说，render 阶段在 React 18 下可以被调度和中断，commit 阶段仍然是同步提交。

### 详细分析

React 渲染大致分两阶段：

- Render：计算下一棵 Fiber 树，找出变更
- Commit：把变更真正提交到 DOM

在早期模型里，render 更接近同步执行。  
在 React 18 的并发能力下，render 阶段可以分片、暂停、恢复、丢弃重来。  
但 commit 阶段为了保证 UI 一致性，仍然要同步完成。

### 可背答案

> React 渲染如果只回答同步或异步其实不够准确。更合理的说法是：React 会先在 render 阶段计算变更，再在 commit 阶段把变更提交到 DOM。在 React 18 里，render 阶段可以被调度、中断和恢复，所以不一定是一路同步跑到底；但 commit 阶段为了保证界面一致性，仍然是同步完成的。  
>   
> 所以 React 的重点不是“异步渲染”，而是“可调度渲染”。

### 注意点

- 不要简单说“React 渲染是异步的”。
- 最好强调 React 18 前后的差异。

### 可能追问

- 为什么 commit 阶段不能中断？
- React 18 的 render 阶段为什么能中断？
- 批量更新和并发渲染是什么关系？

## 7. Diff 规则

### 关键考点

- 你是否理解 React Diff 不是全量树比较。
- 你是否知道 `key` 的作用。

### 短答

React Diff 基于同层比较、类型不同直接替换、列表依赖 `key` 识别复用节点。

### 详细分析

React 为了把复杂度控制在可接受范围，没有做完整树编辑距离算法，而是采用启发式规则：

- 不同类型的节点，直接销毁重建。
- 同层节点比较，不做跨层移动比较。
- 列表场景依赖 `key` 判断节点是否可复用。

所以：

- `key` 稳定时，更新更高效。
- `key` 不稳定或用 index，在插入/删除时容易导致多余更新和状态错位。

### 可背答案

> React Diff 不是全量树最优比较，而是基于几个启发式规则来降低复杂度。第一，不同类型节点直接替换；第二，主要做同层比较，不做跨层深度移动推断；第三，列表更新时依赖 `key` 判断节点是否复用。所以 `key` 的稳定性非常重要，如果乱用 index，列表插入删除时不仅性能会变差，还可能造成组件状态错位。

### 注意点

- 不要说 React 会做最优 Diff。
- 列表题一定要讲到 `key`。

### 可能追问

- 为什么不要用 index 当 key？
- 父子层级变化时会发生什么？

## 8. 如何修改优先级

### 关键考点

- 你是否理解 React 里的优先级是调度优先级，不是手动改一个数值。
- 你是否知道开发者常用的优先级控制入口。

### 短答

开发者通常不会直接操作 Fiber 内部优先级，而是通过 `startTransition`、`useTransition`、`useDeferredValue` 等 API 把某些更新标记成低优先级。

### 详细分析

React 内部有自己的优先级 / lane 调度系统，但业务开发里不直接改内部 lane。  
你能做的是告诉 React：

- 哪些更新是紧急的，比如输入、点击反馈
- 哪些更新是可延后的，比如大列表筛选结果、低优先级视图更新

最常见的手段：

- `startTransition`
- `useTransition`
- `useDeferredValue`

### 可背答案

> React 优先级不是业务里直接改一个内部字段，而是通过调度 API 间接影响。常见做法是把用户输入、点击反馈这类更新保持高优先级，而把大列表过滤、搜索结果刷新、低价值视图更新放进 `startTransition` 或 `useDeferredValue` 里，让 React 延后处理。  
>   
> 所以“修改优先级”更准确地说，是告诉 React 哪些更新更紧急，哪些可以晚一点。

### 注意点

- 不要说“直接修改 Fiber 优先级”。
- 要把优先级和交互场景联系起来。

### 可能追问

- `startTransition` 和防抖有什么区别？
- `useDeferredValue` 适合什么场景？

## 9. 并发渲染是什么，怎么提高渲染优先级

### 关键考点

- 你是否知道并发渲染不是多线程。
- 你是否知道“提高优先级”通常不是手动提升，而是避免把紧急更新放进低优先级流程。

### 短答

并发渲染是 React 18 的可调度渲染机制，它允许 render 阶段被中断、恢复和按优先级处理；所谓提高优先级，本质上是把真正紧急的更新留在高优先级通道里。

### 详细分析

并发渲染解决的问题是：

- 大更新阻塞用户输入
- 低优先级任务拖慢高优先级交互

它不是开多线程，而是：

- 把渲染任务拆成更小的工作单元
- 在需要时暂停低优先级任务
- 先处理更重要的更新

“怎么提高渲染优先级”从业务角度看有两种方式：

- 不要把关键交互包进 transition
- 把非紧急更新降级处理，让关键更新自然更早执行

### 可背答案

> React 并发渲染不是多线程，而是 React 18 提供的一种可调度渲染能力。它让 render 阶段可以被中断、恢复和按优先级重新安排，这样输入、点击这类紧急更新不会轻易被大列表渲染或重计算阻塞。  
>   
> 从业务开发角度，所谓提高渲染优先级，通常不是手动改内部优先级，而是把真正紧急的更新保持在默认高优先级里，把非紧急更新用 `startTransition`、`useTransition` 或 `useDeferredValue` 降级处理。这样关键交互自然就更快响应。

### 注意点

- 不要把并发渲染说成异步多线程。
- 不要把“提高优先级”讲成能直接控制 React 内部调度器。

### 可能追问

- 并发渲染和自动批处理有什么关系？
- 为什么 render 能中断但 commit 不能？

## 10. 前端怎么做数据隔离，A 模块可访问，B 模块不可访问

### 关键考点

- 你是否知道前端权限控制不是最终安全边界。
- 你是否能同时从展示层、路由层、状态层和接口层回答。

### 短答

前端可以做体验层的数据隔离和权限控制，但最终数据隔离必须由后端接口和权限系统保证。

### 详细分析

如果题目里的意思是“模块级权限隔离”，一般要分四层：

**第一层：路由层**

- 无权限用户不进入对应模块
- 动态菜单、路由守卫、重定向

**第二层：展示层**

- 隐藏按钮、入口、表格列、功能区块

**第三层：状态层**

- 不把无权限模块的数据加载到前端
- 按模块和用户角色拆数据访问逻辑

**第四层：接口层**

- 后端按用户身份、角色、租户、资源归属做真正鉴权
- 即使前端构造请求，后端也必须拒绝无权限访问

如果题目是更严格的数据隔离，比如 A 模块和 B 模块多租户隔离，还要强调：

- 数据 scope
- tenantId / orgId
- 服务端资源归属校验

### 可背答案

> 前端能做的是体验层的数据隔离和权限控制，但不能把它当成最终安全边界。通常我会从四层处理：第一层是路由和菜单层，无权限用户看不到模块入口，也进不去对应页面；第二层是展示层，按钮、表格列、操作区按权限显示；第三层是状态层，不去预加载无权限模块的数据；第四层也是最关键的，是后端接口按用户身份、角色、租户和资源归属做真正鉴权。  
>   
> 所以如果题目里说 A 模块可访问、B 模块不可访问，前端负责把体验做对，后端负责把数据真正锁住。

### 注意点

- 不要把“隐藏按钮”说成数据隔离完成了。
- 一定要强调后端才是最终权限边界。
