## 2. 上线后用户看到旧页面，缓存策略怎么处理

### 你的回答问题

- 你答到了 HTML 不缓存、JS/CSS 用 hash 长缓存，这是核心正确点。
- 但面试官追问“网络开销”和“具体缓存策略”时，你没有把 `Cache-Control`、协商缓存、CDN 策略讲清。
- “浏览器默认会缓存”这个说法太泛，面试官想听的是你是否会主动配置缓存策略。

### 正确思路

关键原则：

- HTML：短缓存或 `no-cache`，保证能拿到最新资源清单。
- JS/CSS/image/font：文件名带 contenthash，强缓存长期有效。
- CDN：静态资源长缓存，发布时只新增 hash 文件；必要时刷新 HTML 或入口资源。
- 接口：按业务设置 `Cache-Control`、ETag、服务端缓存或 Next `revalidate`。

### 可背答案

> 这个问题本质是入口文件和静态资源缓存策略要分开。HTML 是资源入口，不能长期强缓存，通常配置 `Cache-Control: no-cache` 或很短的 max-age，让浏览器每次至少和服务器确认；JS、CSS、图片、字体这类静态资源用 contenthash 命名，内容不变 hash 不变，可以配置长期强缓存，比如一年。  
>   
> 这样上线新版本时，用户先拿到新的 HTML，HTML 里引用新的 hash 资源；旧资源因为文件名不同不会被误用，没变化的资源仍然命中缓存，不会产生很大网络开销。CDN 层也按这个原则配置，必要时刷新 HTML 或入口文件。接口缓存则根据业务变化频率单独配置，Next 项目里可以结合 `revalidate` 做页面或数据缓存。

## 3. Tree Shaking 原理

### 你的回答问题

- 你答到了 ESM 和 AST，方向对。
- 但“没有被引用”和“没有被使用”要更准确：打包器通过静态依赖和使用标记判断导出是否被使用。
- 需要补 `sideEffects`、CommonJS 局限和对象整体导出导致 Tree Shaking 失效。

### 正确思路

Tree Shaking 依赖：

- ESM 静态 import/export。
- 构建阶段生成依赖图。
- 标记 used exports。
- 压缩阶段删除 dead code。
- `package.json sideEffects` 辅助判断模块是否有副作用。

### 可背答案

> Tree Shaking 是构建阶段删除未使用代码的优化。它主要依赖 ESM 的静态结构，因为 `import/export` 在编译期就能分析出依赖关系。打包器会构建模块依赖图，标记哪些 export 被真正使用，然后在压缩阶段把未使用代码删除。  
>   
> 这里还要考虑副作用。比如某个模块虽然导出没被用，但执行时会修改全局状态或引入 CSS，就不能随便删，所以很多库会通过 `sideEffects` 标记哪些文件可以安全摇掉。CommonJS 因为是运行时 `require`，静态分析更困难，Tree Shaking 效果通常不如 ESM。

## 4. Vue 3 相比 Vue 2 的性能提升

### 你的回答问题

- 你答到了 `defineProperty` 到 `Proxy`，这是基础点。
- 但只讲响应式不够，Vue 3 性能提升还包括编译优化和运行时优化。

### 正确思路

要讲三层：

- 响应式：`Proxy` 支持属性新增、删除、数组索引等。
- 编译优化：静态提升、Patch Flag、Block Tree。
- 体积和组织：Composition API 更利于逻辑复用，API 支持 Tree Shaking。

### 可背答案

> Vue 3 相比 Vue 2 的性能提升不只在响应式。第一，响应式从 `Object.defineProperty` 改成 `Proxy`，对对象新增属性、删除属性、数组索引等场景支持更自然，也减少了一些初始化递归劫持成本。  
>   
> 第二是编译优化，Vue 3 会做静态节点提升、Patch Flag 和 Block Tree，更新时能更精确地知道哪些动态节点需要 patch，减少无效 diff。第三是 API 设计上更利于 Tree Shaking，Composition API 也让复杂逻辑复用更清晰。

## 5. Webpack 和 Vite 的设计思想区别

### 你的回答问题

- 你说 Webpack 大而全、Vite 快，这个方向对。
- 但“Vite 用 Rollup 写所以快”不准确。Vite 开发态快的核心不是 Rollup。

### 正确思路

- Webpack：bundle-first，启动时先构建依赖图和 bundle。
- Vite：dev server + 原生 ESM，浏览器请求哪个模块才转换哪个模块。
- Vite 依赖预构建用 esbuild，生产构建用 Rollup。

### 可背答案

> Webpack 的设计更偏 bundle-first，开发启动时会从入口开始递归构建依赖图，把模块打成 bundle 后再给浏览器使用，所以项目大了冷启动和热更新成本会变高。  
>   
> Vite 开发态利用浏览器原生 ESM，不需要一开始把所有源码都打包。源码按请求转换，第三方依赖用 esbuild 做预构建，所以冷启动快；修改单个文件时，HMR 也只需要让相关模块失效。生产环境 Vite 再使用 Rollup 做打包优化。所以 Vite 快主要是开发态架构不同，而不是简单因为 Rollup 快。

## 6. Vite 冷启动和热更新

### 你的回答问题

- 这题你现场没答出来，是明显短板。
- 面试官问这个，其实是在追 Vite 和 Webpack 的根本差异。

### 正确思路

- 冷启动：无需全量 bundle，启动 dev server 即可。
- 依赖预构建：把 CommonJS/UMD 转 ESM，并合并依赖，减少请求数。
- HMR：基于模块图精确失效，更新范围更小。

### 可背答案

> Vite 冷启动快，是因为开发环境不需要先把整个项目打成 bundle，而是启动一个 dev server，浏览器通过原生 ESM 请求源码模块，服务端按需转换。  
>   
> 依赖预构建主要解决两个问题：一是把 CommonJS 或 UMD 依赖转成 ESM，二是把很多小模块合并，减少浏览器请求数量。热更新方面，Vite 维护模块依赖图，文件变化后只让相关模块失效，通过 HMR 推送给浏览器，所以比传统全量重新构建快很多。

## 7. Webpack 本地开发启动速度优化

### 你的回答问题

- 你提到缓存、构建耗时分析、关闭 hash、SWC 替代 Babel、升级 plugin，这些都不错。
- 多线程那里被面试官追问是对的，因为 `thread-loader` 不是银弹。
- 可以再补“缩小构建范围”和“source map 策略”。

### 正确思路

优化顺序：

- 先分析耗时。
- 开持久化缓存。
- 缩小 loader 范围。
- 合理 source map。
- esbuild/SWC 替代 Babel/Terser。
- 多线程只给重任务用。
- 减少不必要 plugin。

### 可背答案

> 我优化 Webpack 开发启动速度会先分析，而不是直接上工具。先用 speed-measure-webpack-plugin 或构建 profile 看耗时在哪。然后优先开启 Webpack 5 filesystem cache，缩小 loader 的 include 范围，避免 node_modules 或无关目录参与转换。  
>   
> 开发环境可以降低 source map 成本，关闭不必要的 hash、压缩、产物分析和生产环境插件。转译层可以考虑 SWC 或 esbuild 替代 Babel。多线程要谨慎，只适合比较重的 loader，因为线程创建和通信也有成本，小项目可能反而变慢。

> 微前端的核心是把一个大前端应用拆成多个可独立开发、独立部署、独立运行的子应用，由主应用负责路由分发、子应用加载、挂载和卸载。技术方案可以用 qiankun、single-spa、Module Federation，也可以自研。  
>   
> 真正要处理的难点是隔离和通信。隔离包括 JS 沙箱和样式隔离，避免子应用污染全局变量或样式互相覆盖；通信可以通过主应用下发 props、事件总线、全局 store、URL 参数、CustomEvent 等方式，但要控制边界，不能随便往 `window` 上挂变量。

## 9. 微前端通信怎么做，为什么不能直接挂 `window`

### 你的回答问题

- 你第一反应是共享 `window`，这个容易踩雷。
- 后续提 hash 后缀、symbol 也不是最佳答案，因为根因是全局污染和隔离缺失。

### 正确思路

通信方案：

- 主应用 props。
- event bus。
- shared store。
- URL / route state。
- CustomEvent。
- postMessage。
- Module Federation shared。

隔离：

- Proxy 沙箱。
- 快照沙箱。
- Shadow DOM / CSS Modules / scoped CSS。

### 可背答案

> 微前端通信我不会优先用 `window` 挂变量，因为这会造成命名冲突、状态污染，也不利于子应用卸载清理。更好的方式是根据场景选择通信协议。主应用和子应用可以通过 props 或统一事件总线通信；子应用之间可以通过主应用做中转，或者用 shared store、CustomEvent、URL 状态。  
>   
> 如果必须有全局状态，也要由主应用统一管理，并提供明确 API，而不是各子应用随意写 `window`。同时微前端还要配 JS 沙箱，比如 Proxy 沙箱或快照沙箱，保证子应用挂载时隔离、卸载时恢复。

## 10. TypeScript 工具类型：全部属性可选

### 你的回答问题

- `Partial<T>` 答对了。
- 可以顺手补几个常用工具类型，展现熟练度。

### 正确思路

`Partial<T>` 的本质是 mapped type。

### 可背答案

> 这个可以用 `Partial<T>`。它会把对象类型里的所有属性都变成可选，本质上是 TypeScript 的映射类型。  
>   
> 类似的工具类型还有 `Required<T>` 把属性变必选，`Pick<T, K>` 选部分属性，`Omit<T, K>` 排除部分属性，`Readonly<T>` 只读，`Record<K, T>` 构造键值映射。真实项目里这些工具类型常用于接口 DTO、表单草稿、编辑态数据。

## 11. 类型断言是什么，有什么风险

### 你的回答问题

- 你能解释 `as` 和非空断言，但“工作中场景少”会显得经验不足。
- 更稳的答法要强调断言不是类型转换，只是告诉编译器相信我。

### 正确思路

- 类型断言不改变运行时值。
- 错误断言会掩盖类型问题。
- 优先类型收窄、类型守卫、运行时校验。

### 可背答案

> 类型断言就是开发者告诉 TypeScript：我比编译器更清楚这个值的类型。比如 `value as User` 或非空断言 `user!.name`。但它不会做运行时转换，只是绕过或收窄编译期检查。  
>   
> 风险是如果断言错了，TypeScript 会相信你，运行时仍然可能报错。比如服务端字段变了，你强行断言成某个类型，访问属性时可能就是 undefined。所以我更推荐能用类型收窄就用类型收窄，能用类型守卫或 Zod 这类运行时校验就不要滥用断言。

## 12. 接口签名、加密、Hash 的区别

### 你的回答问题

- 你把接口签名描述成“加密请求参数、服务端解密比对”，这里概念不够准确。
- 签名通常不是“解密”，而是双方用同样规则生成摘要后比对。

### 正确思路

区分：

- 编码：格式转换，可逆，不安全。
- Hash：单向摘要，不可逆。
- 加密：密文可解密。
- 签名：证明请求未被篡改和来源可信。

### 可背答案

> 接口签名严格来说不是加密。常见做法是客户端把请求参数、时间戳、nonce、路径等按固定规则排序拼接，再结合密钥生成 HMAC 或摘要签名，传给服务端。服务端用同样规则重新计算签名并比对，如果一致，说明请求参数没有被篡改。  
>   
> 这里要区分加密和签名。加密强调内容不可见、可解密；hash 是单向摘要；签名更多是完整性和身份校验。为了防重放攻击，还要加 timestamp、nonce 和过期时间。但前端不能保存真正高权限密钥，所以重要签名最好放在服务端或 BFF 层做。

## 13. AI 工具使用怎么讲

### 你的回答问题

- 你能列出 Codex、Claude Code、Cursor 等工具。
- 但面试里不要只报工具名，要讲场景、流程和质量控制。

### 正确思路

按任务粒度：

- Cursor：局部修改、补全、存量项目。
- Codex / Claude Code：跨文件任务、排查、生成测试、文档。
- 流程：需求澄清 -> 任务拆解 -> 小步实现 -> 验证 -> Review。

### 可背答案

> AI 工具我会按场景使用。Cursor 更适合存量项目里的局部修改，比如我已经知道要改哪个文件、哪个函数；Codex 或 Claude Code 更适合跨文件任务，比如排查问题、重构模块、补测试和生成文档。  
>   
> 我不会让 AI 直接无约束写代码。一般会先把需求、边界和验收标准说清楚，让它拆任务，再小步修改。改完后跑 TypeScript、Lint、测试和构建，必要时再让另一个 Agent 做 Review，最后人工确认。核心链路比如权限、支付、SSR、SEO 不能跳过人工 Review。

## 14. 本轮如果复试，最应该补哪几块

### 你的回答问题
