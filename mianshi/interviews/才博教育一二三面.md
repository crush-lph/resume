## 2. 原题：给出一段 `this` 代码，请判断输出；再追问箭头函数场景

### 关键考点

- 是否掌握默认绑定、隐式绑定、显式绑定。
- 是否知道箭头函数没有自己的 `this`。
- 是否能识别 `call/apply/bind` 改变指向。

### 短答

普通函数的 `this` 由调用方式决定；箭头函数的 `this` 在定义时确定，继承外层词法作用域，不能被 `call/apply/bind` 改写。

### 你的现场回答点评

- 前两段普通函数和 `call` 的判断方向是对的。
- 问题出在箭头函数最后一种情况“不太确定”。这会被面试官认为基本概念掌握不牢。
- 这题不能只背“箭头函数没有自己的 this”，还要能顺着题目代码判断“它到底捕获了谁的 this”。

### 详细分析

典型结论：

- `obj.fn()`：`this === obj`
- `fn.call(other)`：`this === other`
- `new Fn()`：`this` 指向新实例
- 箭头函数：没有自己的 `this`，继承定义位置外层作用域

### 实操口径

面试现场如果题目有三四段代码，优先按“函数在哪里定义、怎么被调用、是否是箭头函数”三步判断，不要急着猜输出。

### 可背答案

> `this` 我一般按调用方式判断。对象方法直接调用时，`this` 指向调用它的对象；如果用 `call/apply/bind`，就按显式绑定走；如果是构造调用，则指向新实例。箭头函数比较特殊，它没有自己的 `this`，会在定义时捕获外层作用域的 `this`，所以后面即使再用 `call` 也不会改掉。

### 注意点

- 箭头函数适合回调，不适合对象原型方法。
- 在模块顶层和浏览器全局里的 `this` 语义要区分。

### 可能追问

- 箭头函数能做构造函数吗？
- `bind` 和 `call` 的区别是什么？
- 事件处理里的 `this` 怎么看？

## 3. 原题：给出宏任务、微任务混合代码，请口述完整输出顺序

### 关键考点

- 是否清楚同步、微任务、宏任务的执行顺序。
- 是否知道每轮宏任务之后会清空微任务。
- 是否能准确分析代码输出。

### 短答

先执行同步任务，当前调用栈清空后，先清空微任务队列，再进入下一个宏任务；每执行完一个宏任务，都会再次清空微任务。

### 你的现场回答点评

- 你整体顺序分析是对的，说明事件循环主干没问题。
- 但如果要更稳，最好把“`Promise` 构造器同步执行，`then` 才入微任务”明确说出来。
- 如果代码里有“微任务中再创建微任务”，要特别强调仍会在本轮继续清空，不然容易被追问。

### 详细分析

常见分类：

- 宏任务：`setTimeout`、`setInterval`、I/O、UI render 相关调度。
- 微任务：`Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`。

关键点：

- `new Promise(executor)` 中 executor 同步执行。
- `then` 回调才进入微任务。
- 微任务执行中新增的微任务，会继续在本轮清空。

### 实操口径

这题最好按“同步日志 -> 微任务 -> 第一个宏任务及其微任务 -> 第二个宏任务”这样现场口述，不要跳步。

### 可背答案

> 事件循环我会按执行阶段来看。首先执行所有同步代码；遇到 Promise 构造器会立即执行 executor，`then` 回调进入微任务队列；`setTimeout` 进入宏任务队列。同步栈清空后，先把所有微任务一次性清掉，再执行下一个宏任务。每个宏任务执行完，又会重新清空微任务，所以如果某个 `setTimeout` 里继续产生 Promise 微任务，这个微任务会先于后续宏任务执行。

### 注意点

- `Promise.resolve().then(...)` 是微任务，不要说成异步“立刻执行”。
- 微任务清空发生在渲染前后不同环境中细节会更复杂，但基础题按规范回答即可。

### 可能追问

- `async/await` 和微任务怎么对应？
- `queueMicrotask` 和 `Promise.then` 区别？
- 浏览器和 Node 事件循环有何不同？

## 4. 原题组：字符串中的 A 全部替换为 B；`useMemo` 和 `useCallback` 区别；`Map` 和 `Object` 区别；`forEach` 如何中断；`reduce` 怎么用

### 关键考点

- `replaceAll` 与正则 `replace`
- `useMemo` / `useCallback`
- `Map` / `Object`
- `forEach` 跳出
- `reduce`

### 短答

这组题重点不是定义，而是“知道 API 边界，知道更推荐的写法”。

### 你的现场回答点评

- 字符串替换回答基本正确，`replaceAll` + 正则兜底是合格的。
- `useMemo/useCallback` 回答正确，但略短，最好补一句它们解决的是“重复计算”和“函数引用稳定性”。
- `Map/Object` 只说“Map 有迭代器”偏弱，没说到 key 类型、增删性能和语义差异。
- `forEach` 通过抛异常退出虽然能做到，但不是好答案。面试更希望听到“换循环结构”。
- `reduce` 的回答过于概念化，最好能举一个求和、分组或转索引对象的例子。

### 详细分析

- 全部替换：
  - `str.replaceAll("A", "B")`
  - 或 `str.replace(/A/g, "B")`
- `useMemo` 缓存计算结果；`useCallback` 缓存函数引用。
- `Map`：
  - key 可以是任意类型。
  - 天然可迭代，适合频繁增删。
- `Object`：
  - 更像普通记录结构。
  - key 最终会转字符串或 symbol。
- `forEach` 不能 `break/continue/return` 终止整体循环。
  - 真有中断需求，用 `for...of`、`some`、`every`、`find`。
- `reduce` 适合聚合成单一结果，比如求和、分组、对象映射。

### 实操口径

如果现场问“forEach 怎么中断”，我会明确说“不推荐抛异常”，因为这不是语义化控制流。真实开发会直接换循环方式。

### 可背答案

> 全量替换字符串可以用 `replaceAll`，兼容性更稳时可以用正则全局替换 `str.replace(/A/g, "B")`。  
>   
> React 里 `useMemo` 主要缓存值，`useCallback` 主要缓存函数引用，避免子组件因引用变化重复渲染。`Map` 适合做动态键值映射和频繁增删，`Object` 更适合普通结构化数据。  
>   
> `forEach` 本身不能正常中断，如果需要提前结束，我会换成 `for...of`、`some` 或 `find`，不建议用抛异常这种方式。`reduce` 则适合把一组数据归并成一个结果，比如求和、分组或转换成对象索引。

### 注意点

- 不要把 `Map` 的优势只说成“有迭代器”。
- `useMemo` 不应滥用。

### 可能追问

- `Map` 和 `WeakMap` 区别？
- `useMemo` 什么时候反而没有意义？
- `reduce` 怎么实现 `groupBy`？

## 5. 原题：实现一个倒计时，并继续追问如何减少重渲染、为什么 `setInterval` 不准、如何解决闭包陷阱

### 关键考点

- 基础实现
- 定时器精度
- React 重渲染控制
- 闭包陷阱

### 短答

倒计时不能只写 `setInterval`，还要处理“渲染粒度、时间漂移、后台节流和闭包拿旧值”。

### 你的现场回答点评

- “拆成最小粒度组件”这个点是对的，说明你有 React 性能意识。
- 对 `setInterval` 不准的根因，回答到“事件循环和后台节流”是对的。
- 但“用 `requestAnimationFrame` 会更准”这个说法不够准确。倒计时更关键的是记录目标结束时间，再用当前时间校准，而不是依赖某个调度 API 更准。
- 闭包陷阱你提到 `useRef` 是可行方案，但更基础的标准答案还应包含“函数式更新”。

### 详细分析

推荐方案：

- 用目标结束时间 `endAt` 而不是只存剩余秒数。
- 每次 tick 通过 `Date.now()` 重新计算剩余时间，避免漂移累计。
- 定时器状态收敛在最小组件里，减少上层大组件渲染。
- 最新状态通过函数式更新或 `useRef` 读取。

示例思路：

```ts
const endAtRef = useRef<number>(0);

function start(durationMs: number) {
  endAtRef.current = Date.now() + durationMs;
}

function tick() {
  const left = Math.max(0, endAtRef.current - Date.now());
  setLeft(left);
}
```

### 实操口径

如果倒计时出现在支付页、活动页、验证码页，我会把它封装成独立组件或 Hook，只上报必要事件；切后台回来后按真实时间重新校准，而不是相信 interval 次数。

### 可背答案

> 倒计时基础上可以用 `setInterval`，但生产里我会注意三个问题。第一是渲染粒度，如果它放在一个很大的页面组件里，每秒 `setState` 会带来额外渲染，所以我会封成独立组件或 Hook。第二是精度，浏览器后台标签页会节流定时器，所以我不会只做 `count--`，而是记录结束时间，每次用 `Date.now()` 算剩余值，回来后自动校准。第三是闭包，如果 interval 回调一直拿到旧 state，我会用函数式更新或 `useRef` 保存最新值。

### 注意点

- `requestAnimationFrame` 不适合单独解决“后台标签页计时准不准”这个问题。
- 对秒级倒计时，用结束时间校准比追求 tick 精准更重要。

### 可能追问

- 页面 hidden 后怎么处理？
- 倒计时归零后如何保证只触发一次回调？
- 如何设计一个通用 `useCountdown`？

## 6. 原题：Webpack 和 Vite 有什么区别；为什么 Vite 快；做过哪些 Taro 多端问题

### 关键考点

- Vite 快的根因
- 构建态与开发态差异
- Taro 跨端兼容
- `patch-package`
- `CustomWrapper`

### 短答

Vite 开发态快的关键是原生 ESM、按需转换、依赖预构建；Taro 的难点则在运行环境差异和第三方生态兼容。

### 你的现场回答点评

- Taro 部分回答比较有实战味，`patch-package` 和 `CustomWrapper` 都是加分项。
- Vite 部分不够准。说“底层 Rollup，所以快”会被追问，因为开发态速度核心不是 Rollup。
- 更稳的回答要拆开开发态和生产态：开发态 ESM + 按需转换 + esbuild 预构建，生产态 Rollup。

### 详细分析

Vite：

- 开发态利用原生 ESM，不先整包构建。
- 请求到哪个模块就转换哪个模块。
- 依赖预构建通常依赖 esbuild，提高冷启动和依赖加载速度。
- 生产构建常用 Rollup。

Taro：

- 生态差异：H5 可用库，小程序端未必能跑。
- 兼容方案：替代库、条件编译、`patch-package` 修补三方包。
- 性能：页面级状态更新可能影响较大渲染范围，`CustomWrapper` 可把更新范围收敛到局部。

### 实操口径

这块可以结合你真实小程序项目：ECharts 兼容问题、分包、主包体积治理、`CustomWrapper` 优化页面级更新。

### 可背答案

> Vite 开发态快，我会重点说三点：原生 ESM、按需转换、依赖预构建。它不是像 Webpack 一样先把所有东西打成 bundle 再启动服务，而是浏览器请求到哪里就处理哪里；第三方依赖还会先预构建，减少后续成本。生产构建层面再交给 Rollup 完成。  
>   
> Taro 的难点主要是多端环境差异。比如有些图表库 H5 能用，小程序不一定能跑，这种情况我会看是否有替代方案，必要时用 `patch-package` 修补。性能方面，如果页面级状态变化引发大面积更新，我会用 `CustomWrapper` 之类的能力把影响范围收敛到局部。

### 注意点

- 不要把 Vite 快简单归因成“Rollup 比 Webpack 快”。
- Taro 的跨端不是“写一次到处完全一样”，要讲差异处理。

### 可能追问

- Vite 为什么还需要依赖预构建？
- 小程序和 H5 运行环境差异有哪些？
- `patch-package` 的风险是什么？

## 7. 原题：小程序主包接近上限，首页和订单页加载慢，怎么优化

### 关键考点

- 主包 / 分包边界
- 首页与订单页慢的处理
- 包体分析
- 首屏依赖治理

### 短答

主包只放首屏和 tabBar 必要内容，非关键模块进分包；性能优化要同时看包体、资源、接口和页面渲染。

### 你的现场回答点评

- “tabBar 页面放主包，其他放分包”这个方向对。
- 但面试官如果继续追“为什么这么拆、独立分包怎么用、公共依赖怎么处理”，你现场准备还不够。
- 首页慢的回答里提到 `preconnect`，这个是 Web 思路，放到小程序题里会有些跑偏。更应该优先讲分包预下载、图片、接口并发、首屏骨架和本地缓存。

### 详细分析

分包原则：

- tabBar 必要页面、启动即访问模块放主包。
- 低频页面、非首屏页面、重依赖模块放分包。
- 公共依赖要避免被错误打回主包。

性能优化：

## 9. 原题：口述手写 `Promise.all`；再问 `Promise.all` 和 `Promise.race` 的区别

### 关键考点

- 保序
- 非 Promise 值处理
- 空数组
- 任一 reject 立即失败

### 短答

`Promise.all` 要保持结果顺序、支持普通值、空数组直接 resolve、任一失败立即 reject；`race` 返回最先 settle 的结果。

### 你的现场回答点评

- “计数器 + 任一失败 reject”这个主干是对的。
- 但你漏了几个高频细节：结果数组必须按输入顺序、普通值也能兼容、空数组直接 resolve。
- 这类手写题，面试官通常就是看这些边界条件。

### 详细分析

`Promise.all` 关键点：

- `Promise.resolve(item)` 统一包装。
- `results[index] = value` 保序。
- `count === arr.length` 时 resolve。
- 空数组直接 resolve `[]`。
- 一个失败立刻 reject。

### 实操口径

如果现场不写完整代码，至少把这四个边界讲出来，比只说“计数器”更稳。

### 可背答案

>   
> `Promise.race` 则是哪个 Promise 最先 settled，就用它的 fulfilled 或 rejected 结果结束。

### 注意点

- “先完成先放入结果数组”是错的。
- `race` 的“先完成”包括 reject。

## 11. 原题：`unknown`、`any`、`never` 的区别和使用场景

### 关键考点

- 类型安全程度
- 使用前是否需要收窄
- `never` 的标准场景

### 短答

`any` 是放弃类型检查；`unknown` 是类型未知但仍要求先收窄；`never` 表示不可能出现，常用于永不返回函数或穷尽检查。

### 你的现场回答点评

- `unknown` 和 `any` 的差异说对了。
- 但“先断言 unknown 再断言具体类型”这个说法不够好，容易让人感觉你是在绕过类型系统。更推荐回答“先做类型守卫收窄”。
- `never` 说“基本没用过”会失分，至少要记住穷尽检查和不可能返回的函数这两个标准场景。

### 详细分析

- `any`：编译器基本不限制，风险最高。
- `unknown`：不能直接使用，必须先判断。
- `never`：
  - 抛错函数的返回类型。
  - 无限循环函数。
  - 联合类型穷尽检查。

示例：

```ts
function assertNever(x: never): never {
  throw new Error(`unexpected value: ${x}`);
}
```

### 实操口径

在接口数据、第三方 SDK 返回值不可信时，用 `unknown + 类型守卫`；在状态机或判别联合类型里，用 `never` 做穷尽检查，防止新增分支漏处理。

### 可背答案

> `any` 相当于告诉 TypeScript 不要管我，类型安全最弱；`unknown` 也是未知类型，但不能直接访问属性，必须先做类型收窄，所以更安全。工作里我更愿意用 `unknown` 接住不可信数据，再用类型守卫判断。  
>   
> `never` 表示不可能出现的类型，典型场景是抛错函数、死循环函数，或者在联合类型里做穷尽检查。比如 switch 处理所有状态后，剩余分支应该是 `never`，这样以后新增状态时编译器能提醒我漏处理。

### 注意点

- “先断言成 unknown 再断言具体类型”不是最优口径，优先说类型守卫。
- `never` 不是“基本不用”，它在类型设计里很有价值。

AI 生成代码的核心风险是“看起来对，长期不可维护”，所以要在需求规格、测试、规范、Review 和高风险边界上加护栏。

### 你的现场回答点评

- 这题你的框架是好的：SDD、测试、规范注入、交叉 Review、人工 Review，整体方向正确。
- 如果再往上提一级，可以把它收束成“输入约束、过程验证、结果验收、资产沉淀”四层，会更像体系化回答。
- 需要避免把“用另一个 AI Review”说得过重，它只能辅助，不能替代人。

### 详细分析

可以分四层：

- 输入层：先明确需求、边界、任务清单。
- 生成层：给 AI 注入项目规范、目录约束、接口约束。
- 验证层：单测、E2E、类型、Lint、构建。
- 审核层：人工 Review 架构合理性、职责划分、安全边界。

### 实操口径

结合你已有 Vibe Coding / Skill 实践，讲“AI 先草拟，工程师定边界和验收”，非常适合。

### 可背答案

> AI 生成代码的可维护性问题，本质上是它是概率系统，能给出一个看似合理的答案，但不保证最适合当前项目。所以我会把控制点前移和后移。  
>   
> 前移是 SDD 或规格驱动：先把需求、边界、任务拆解和验收标准讲清楚，再让 AI 生成。后移是质量门禁：TypeScript、Lint、单测、E2E、构建，再加人工 Review。对于核心函数、权限、支付、SSR 这类高风险链路，AI 只能辅助，不能直接免审合并。必要时还可以让另一个模型做交叉 Review，但最终责任仍然在人。

## 16. 原题：门外三个开关控制房间里三盏灯，只能进房间一次，怎么判断对应关系；追问如果是 LED 灯呢

### 关键考点

- 利用额外状态变量思考问题。
- 能否承认方案依赖前提。

### 短答

经典解法依赖灯会发热这一物理条件；如果换成 LED，原方案不成立，必须承认前提变化。

### 你的现场回答点评

- 白炽灯版本你的思路是对的。
- 面试官追问 LED 时，本质是在看你会不会识别前提失效。这里不需要硬造新解法，承认“信息量不够，原方案失效”更好。

### 详细分析

白炽灯场景：

- 开关 A 开一会再关。
- 开关 B 打开。
- C 不动。
- 进屋后：
  - 亮的 = B
  - 灭但热 = A
  - 灭且冷 = C

LED 场景：

- 如果不能借助发热、声音、联网、透光等额外信息，单次进入无法唯一确定全部映射。

### 实操口径

这题不是要硬凑答案，而是要体现“识别前提依赖”。面试官追问 LED，正确姿势是承认原解法失效，并说明信息量不足。

### 可背答案

> 白炽灯场景下，可以利用“亮灭”和“温度”两个维度编码信息：先开 A 一段时间再关，打开 B，C 不动；进去后亮的是 B，灭但热的是 A，灭且冷的是 C。  
>   
> 但如果换成 LED 且它几乎不发热，同时又不允许额外观察或中途进房间，那这个方案就失效了。因为你只剩亮和灭两个状态，信息量不够区分三个开关。我会直接说明这个解法依赖物理前提。

### 注意点

- 不要被追问后硬编。
- 这题看的是思维严谨性，不是灯泡知识。

### 可能追问

- 如何抽象成信息编码问题？
- 还有没有其他借助外部状态的解法？

## 17. 原题：代码 Review 的原则是什么

### 关键考点

- Review 看什么
- 优先级排序
- 如何给建设性反馈

### 短答

代码 Review 不只是找语法错，而是优先看正确性、边界、安全、可维护性和是否符合项目约束。

### 你的现场回答点评

- 这是三面题，面试官想看你的工程观和协作方式。
- 如果只讲“规范、命名、格式”，会显得层次低。
- 更好的答法是把 Review 分成 blocker / suggestion，并先看正确性与风险。

### 详细分析

Review 可以分层：

- 需求正确性：是不是解决了正确的问题。
- 逻辑边界：异常、空态、重复点击、竞态。
- 架构边界：职责是否清晰，是否破坏分层。
- 性能与安全：无谓重渲染、XSS、权限、接口暴露。
- 可读性：命名、抽象、重复代码。
- 验证：测试、日志、监控是否充分。

### 实操口径

我会先指出阻塞合并的问题，再提非阻塞建议。核心链路 Review 更严格，样式类小改动 Review 重点不同。

### 可背答案

> 我做 Code Review 会先看正确性和风险，而不是先挑格式。第一，需求是不是实现对了；第二，异常和边界有没有覆盖；第三，是否破坏模块边界和已有约束；第四，再看性能、安全、可读性和测试。  
>   
> 反馈方式上，我会区分 blocker 和 suggestion。会影响功能、稳定性、安全性的必须改；命名、抽象和代码风格如果不影响主路径，可以用建议形式沟通。这样 Review 才既能控质量，也不会把协作搞得很僵。

### 注意点

- 不要把 Review 说成“看代码规范”。
- 要有风险意识和沟通意识。

### 可能追问

- AI 生成代码你怎么 Review？
- 哪些问题必须卡合并？
- 如果对方不认同怎么办？

## 18. 原题：什么是面向对象

### 关键考点

- 封装、继承、多态
- 和前端实际开发的联系
- 不要把 OOP 讲成背定义

### 短答

面向对象是一种围绕“对象的状态和行为”组织代码的方法，核心思想是封装变化、复用共性、通过多态适配差异。

### 你的现场回答点评

- 这是基础题，但三面问它往往不是只想听定义，而是看你能不能结合业务理解抽象。
- 如果只背“封装继承多态”，会比较薄。
- 结合你的支付策略模式项目来答，会自然很多。

### 详细分析

- 封装：隐藏内部实现，只暴露必要接口。
- 继承：复用已有抽象，但要谨慎层级过深。
- 多态：同一接口，不同实现。

前端场景：

- 支付策略实现共同接口。
- 图表组件、表单字段、上传适配器。
- 编辑器命令对象。

### 实操口径

结合你支付策略模式项目最合适：不同支付渠道共享统一接口，这其实就是多态思想在业务里的体现。

### 可背答案

> 面向对象不是单纯写 class，而是一种组织复杂度的方式。它把数据和行为封装到对象里，通过封装隐藏内部细节，通过继承或组合复用共性，通过多态让同一接口适配不同实现。  
>   
> 在前端业务里，我更常见的是“面向接口设计”。比如支付中心里，不同渠道都实现统一的 `createOrder`、`pay`、`queryStatus` 这类能力，上层业务不关心底层是 Stripe、微信还是别的渠道，这就是多态思想的落地。

### 注意点

- 不要只背“封装继承多态”。
- 前端里组合往往优于深继承。

- 面向对象和函数式区别？
- 组合为什么优于继承？
- 策略模式和多态是什么关系？
