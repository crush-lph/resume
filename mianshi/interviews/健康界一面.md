# 健康界一面面经

面试日期：2026-05-08  
岗位方向：React / Next.js / AI 前端工程化  
题型特点：性能优化、Next.js 部署、AI 开发范式、工程验证体系

## 本轮考点

- 性能优化：指标定位、资源治理、渲染优化、线上监控闭环
- Next.js 部署流程：SSR 服务模式、静态资源、Standalone、容器化、灰度和回滚
- 负载均衡：七层入口、服务实例、无状态部署、会话和缓存一致性
- SDD 开发范式：Specification Driven Development，先规格后实现
- Vibe Coding Harness Engineering：任务规格、执行边界、验证流水线、Skill 资产回归

## 总体复盘

这轮问题更偏工程落地，不只是问“你会不会性能优化”或“Next.js 怎么部署”，而是会追真实项目里怎么上线、怎么扩容、怎么验证、怎么保证 AI 辅助开发不失控。

回答策略：

- 性能题不要直接背优化清单，先讲指标和定位链路。
- Next.js 部署题要区分纯静态、Node SSR、Standalone、容器化这几种模式。
- SDD 题要回答“我如何把需求变成可执行规格”；Harness Engineering 题要回答“我如何让 Vibe Coding 可约束、可验证、可复盘、可沉淀”。
- 如果没有明确做过某个框架，不要硬说做过，改成“我在项目里类似实践是...”。

## 1. 性能优化

### 关键考点

- 是否能按指标定位瓶颈，而不是直接堆优化手段。
- 是否理解前端性能包括网络、资源、渲染、交互、服务端响应。
- 是否能结合 Next.js / React 项目讲真实落地。
- 是否知道上线后要通过 RUM 和监控持续回看。

### 短答

性能优化我会先定指标，再定位瓶颈，最后按首屏、资源、渲染、交互和服务端链路分层优化，并通过线上监控验证是否真的改善。

### 详细分析

性能优化不能一上来就说“懒加载、缓存、压缩”，因为不同瓶颈对应的方案不一样。

**第一步：确定目标指标**

- 首屏类：TTFB、FCP、LCP。
- 交互类：INP、长任务、主线程阻塞时间。
- 稳定性：CLS、错误率、资源加载失败率。
- 业务指标：转化率、跳出率、留存、关键页面完成率。

**第二步：定位问题来源**

- TTFB 高：可能是服务端接口慢、SSR 数据依赖重、缓存策略不合理。
- LCP 高：可能是首屏大图、字体阻塞、关键 CSS/JS 过大、接口阻塞。
- INP 差：可能是主线程长任务、重复渲染、重计算、大列表、事件处理太重。
- CLS 高：可能是图片尺寸未固定、广告/动态模块插入、字体替换造成布局变化。

**第三步：按层优化**

- 资源层：代码分割、Tree Shaking、图片压缩、WebP/AVIF、多尺寸图片、字体子集化。
- 网络层：CDN、HTTP 缓存、接口缓存、预加载关键资源、减少串行请求。
- 渲染层：组件拆分、`memo`、`useMemo`、`useCallback`、虚拟列表、减少不必要状态提升。
- React 层：避免大组件全量重渲染，把高频状态隔离到局部或外部 store。
- Next.js 层：合理选择 SSR / SSG / ISR / CSR，Server Component 减少客户端 JS，动态组件按需加载。
- 监控层：接入 Web Vitals、接口耗时、错误率、页面性能趋势，避免优化后回退。

### 实操口径

如果我讲 FastMoss 这类 Next.js 项目，我会说性能优化是从 SEO 页面和核心落地页开始做的。先用 Lighthouse、Performance、React Profiler 和线上 RUM 看 FCP、LCP、接口耗时、JS 包体和长任务；再把公开内容页放到更适合 SEO 和首屏的渲染模式里，首屏图片、字体、数据请求和大依赖逐个治理；最后上线后持续看 Core Web Vitals 和业务转化，不把性能优化停留在本地分数。

### 可背答案

> 我做性能优化一般不会先报一堆方案，而是先看指标。比如首屏慢，我会先拆 TTFB、FCP、LCP，看是服务端响应慢、接口慢、资源太大，还是渲染阻塞；交互卡顿就看 INP、长任务、React 重渲染和大列表。  
>   
> 具体落地上，资源层会做拆包、图片和字体优化、CDN 和缓存；渲染层会做组件拆分、虚拟列表、缓存重计算、减少无效 render；Next.js 项目里还会按页面选择 SSR、SSG、ISR 或 CSR，避免所有页面都用同一种模式。最后我一定会接线上监控，看 Web Vitals、接口耗时、错误率和业务指标有没有真实改善。

### 注意点

- 不要只说“懒加载、缓存、压缩”，这太像背八股。
- 不要只讲前端资源，SSR 项目还要考虑服务端响应和接口链路。
- 不要只讲 Lighthouse，本地分数不能代表全部真实用户体验。

### 可能追问

- LCP 高你会怎么排查？
- INP 差通常是什么原因？
- Next.js 项目性能优化和普通 SPA 有什么区别？
- 优化上线后怎么防止指标回退？

## 2. Next.js 部署流程，什么模式，负载均衡怎么实现

### 关键考点

- 是否理解 Next.js 不只是静态文件，也可能需要 Node 服务。
- 是否能区分 `output: export`、`next start`、`output: 'standalone'`、Vercel/容器化部署。
- 是否知道 SSR 服务应该无状态部署，前面通过 Nginx / SLB / Ingress 做负载均衡。
- 是否理解静态资源和动态 SSR 请求的部署路径不同。

### 短答

Next.js 部署要先看项目采用什么渲染模式：纯静态可以导出静态产物走 CDN；如果有 SSR、Route Handler、Middleware、动态 Metadata 等服务端能力，就需要运行 Node 服务。生产环境常见做法是构建 standalone 产物，打 Docker 镜像，部署多实例，前面用 Nginx、云负载均衡或 Kubernetes Ingress 做七层转发。

### 详细分析

Next.js 常见部署模式有几类：

**第一类：静态导出**

适合纯静态站点或不依赖服务端运行时的页面。

```js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'export',
}

export default nextConfig
```

这种模式构建后产物可以放到 CDN、对象存储或静态服务器上，但不适合依赖 SSR、动态接口、服务端鉴权的页面。

**第二类：Node 服务模式**

适合有 SSR、App Router、Route Handler、动态 Metadata、服务端鉴权、BFF 聚合等需求的项目。常规链路是：

```bash
pnpm install
pnpm build
pnpm start
```

或者用 `next start` 启动生产服务。

**第三类：Standalone 部署**

Next.js 支持 `output: 'standalone'`，构建时会基于输出文件追踪生成一个最小运行目录，只包含生产运行需要的文件和依赖。

```js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone',
}

export default nextConfig
```

构建后常见启动方式：

```bash
node .next/standalone/server.js
```

如果部署到容器里，一般还要把 `public` 和 `.next/static` 放进 standalone 运行目录，或者让静态资源走 CDN。

**第四类：平台化部署**

如果用 Vercel，很多构建、边缘网络、缓存、回滚能力由平台托管。国内或企业内网更常见的是自建 CI/CD + Docker + Kubernetes / 云服务器 / Nginx。

**负载均衡怎么实现**

负载均衡通常不是 Next.js 自己做，而是在 Next.js 服务前面加入口层：

```txt
用户
  -> CDN
  -> Nginx / SLB / Kubernetes Ingress
  -> Next.js Node 服务实例 A/B/C
  -> 后端 API / Redis / 数据库
```

核心注意点：

- Next.js 服务尽量无状态，用户态放 cookie、token、Redis 或后端 session，不要依赖单机内存。
- 静态资源走 CDN 或对象存储，动态 SSR 请求打到 Node 服务。
- 多实例部署时要配置健康检查，异常实例自动摘除。
- 环境变量、构建版本、缓存策略要统一，避免不同实例返回不一致内容。
- 灰度发布时可以按流量比例、用户维度或路径维度切流。

### 实操口径

如果让我讲实际部署，我会按“构建产物分层”来说：`/_next/static`、图片、字体这些静态资源尽量走 CDN；需要 SSR 的页面和接口由 Node 服务承接；Next.js 服务用 Docker 打成镜像，CI 里安装依赖、跑检查、构建 standalone，再发布到测试/预发/生产。生产环境前面挂 Nginx 或云负载均衡，多实例无状态部署，健康检查失败就摘流。上线后看服务错误率、SSR 响应耗时、接口错误率和 Web Vitals。

### 可背答案

> Next.js 部署我会先看项目模式。如果是纯静态页面，可以 `output: export` 后把产物放 CDN 或对象存储；但如果项目用了 SSR、动态 Metadata、Route Handler、服务端鉴权这些能力，就必须跑 Node 服务。生产上我更倾向用 `output: 'standalone'` 生成最小运行产物，再打 Docker 镜像部署。  
>   
> 负载均衡一般放在 Next.js 前面，比如 CDN 后接 Nginx、云 SLB 或 Kubernetes Ingress，再转发到多个 Next.js Node 实例。这里关键是服务要无状态，静态资源走 CDN，动态 SSR 请求走 Node；多实例配健康检查、灰度、回滚和日志监控。这样扩容时加实例就行，不会被单机状态绑住。

### 注意点

- 不要把 Next.js 部署说成“打包后扔 nginx”这么简单，SSR 项目需要 Node 运行时。
- `output: export` 不适合所有 Next.js 项目，尤其不适合动态服务端能力。
- Standalone 模式下官方文档建议用生成的 `server.js` 启动，而不是简单等同于普通 `next start`。
- 负载均衡要强调 Next 服务无状态，否则多实例会有会话一致性问题。

### 可能追问

- SSR 页面为什么不能只放 CDN？
- Standalone 模式解决了什么问题？
- 多实例下 session 怎么处理？
- 灰度发布怎么做？
- 如果某个实例缓存脏了怎么办？

## 3. SDD 开发范式的实践，使用了什么框架

### 关键考点

- 是否理解 SDD 是先定义规格，再让实现围绕规格展开。
- 是否能把 AI Coding 和传统工程规范结合起来。
- 是否知道规格可以包括需求、接口、状态、异常、验收标准、测试。
- 是否能说清用什么工具或框架把规格落地。

### 短答

我理解的 SDD 是 Specification Driven Development，也就是规格驱动开发。它不是先让 AI 或开发直接写代码，而是先把需求、边界、接口、状态、异常和验收标准写成结构化规格，再基于规格生成实现、测试和文档。

### 详细分析

SDD 的核心不是某一个工具，而是一套流程：

**第一步：写规格**

规格里至少包含：

- 业务目标：要解决什么问题。
- 用户路径：用户怎么进入、怎么操作、成功态是什么。
- 状态模型：loading、success、empty、error、permission denied。
- 接口契约：请求参数、响应字段、错误码、鉴权方式。
- 边界场景：弱网、重复点击、接口超时、权限不足、数据为空。
- 验收标准：什么情况下算完成，哪些指标不能退化。

**第二步：规格评审**

先让产品、前端、后端、测试对齐规格，避免开发过程中才发现边界不一致。

**第三步：基于规格实现**

前端可以根据规格拆：

- 页面路由
- 组件结构
- 状态机
- 请求层
- 类型定义
- 错误处理
- 埋点和监控

**第四步：基于规格验证**

测试用例、Mock 数据、接口联调、异常场景和回归清单都从规格生成或对照规格检查。

**使用什么框架**

如果面试官问框架，我会分两类回答：

- 研发流程框架：PRD / RFC / ADR / Checklist / 验收标准。
- 技术落地框架：TypeScript、OpenAPI / Swagger、Zod、MSW、React Testing Library、Playwright、Storybook、ESLint、CI。

AI 编程场景下，也可以把规格沉淀成项目级 Prompt / Skill，让 AI 每次都按固定结构输出：

- 先复述需求和边界。
- 再拆任务。
- 再生成代码。
- 再补测试和自检清单。

### 实操口径

如果结合我现在沉淀面经 Skill 的思路，我会说 SDD 在团队里可以落成“规格模板 + AI 执行 + 人工 Review + 自动化验证”。比如做一个支付功能，不会直接让 AI 写页面，而是先写清楚渠道、订单状态、支付状态、轮询规则、异常兜底、埋点和验收标准；然后让 AI 按规格生成策略接口、状态流转和测试用例。这样 AI 产出更稳定，Review 也有依据。

### 可背答案

> SDD 我理解是规格驱动开发。它的重点不是换一个框架，而是把“需求是什么、边界是什么、接口怎么约定、异常怎么处理、验收标准是什么”先结构化写清楚，再进入实现。  
>   
> 实操里我会用 TypeScript 保证类型契约，用 OpenAPI 或 Swagger 对齐接口，用 Zod 做运行时校验，用 MSW 做接口 Mock，用 React Testing Library 或 Playwright 做关键链路验证。如果结合 AI Coding，我会把这些规格沉淀成 Prompt 或项目级 Skill，让 AI 先按规格拆任务，再写代码、测试和自检清单。这样比直接让 AI 生成代码稳定很多。

### 注意点

- 不要把 SDD 说成“写文档”，它的核心是让规格进入实现和验证链路。
- 不要硬编某个没用过的框架，可以说“我用过类似实践”。
- 要强调 AI 场景下 SDD 的价值：减少歧义，提高产出确定性。

### 可能追问

- SDD 和 TDD 有什么区别？
- 规格写太多会不会降低效率？
- 如何保证规格和代码不脱节？
- AI 生成代码时 SDD 怎么起作用？

## 4. Vibe Coding 实践中的 Harness Engineering

### 关键考点

- 是否理解 Harness 在这里指 Vibe Coding 的工程护栏，不是普通测试脚本。
- 是否能把 AI 编码任务从“临时对话”变成“可复用任务规格 + 可验证产出”。
- 是否知道如何约束 Agent 读写范围、执行命令、修改文件和输出格式。
- 是否能讲清 Prompt / Skill / 模型变化后，如何用固定任务集回归质量。

### 短答

在 Vibe Coding 实践里，Harness Engineering 可以理解成给 AI 编码建立一套工程化运行框架：把需求输入、上下文材料、可用工具、文件边界、验证命令、Review 清单和沉淀资产固定下来，让 AI 不是随便写代码，而是在可控环境里交付可验证结果。

### 详细分析

Vibe Coding 很容易被误解成“打开 AI 工具，边聊边写”。但在团队里真要落地，不能只靠个人手感，因为 AI 可能会：

- 理解错需求。
- 改到不该改的文件。
- 生成和项目风格不一致的代码。
- 忘记补测试或验证。
- 把一次有效 Prompt 留在聊天记录里，后续无法复用。
- 模型或工具升级后，原来稳定的产出突然退化。

所以 Vibe Coding 里的 Harness，本质是把 AI 编码过程做成一套“可约束、可验证、可复盘、可沉淀”的工程流程。

可以按四层讲：

**第一层：任务规格 Harness**

- 每类任务先有固定规格，而不是一句“帮我改一下”。
- 规格包含：背景、目标、输入材料、涉及模块、禁止修改范围、验收标准。
- 比如 Bug 修复任务要求 AI 先复现、再定位、再改动、再跑测试。
- 比如组件开发任务要求 AI 先确认 props、状态、空态、错误态、交互态和响应式。
- 比如面经沉淀任务要求固定输出结构：本轮考点、实操口径、可背答案、可能追问。

**第二层：执行环境 Harness**

- 限定 Agent 能看的上下文：README、架构文档、相关代码、规范文档、Skill。
- 限定 Agent 能改的文件范围，避免大范围重构或误改无关模块。
- 规定执行顺序：先读代码，再给方案，再改文件，再验证。
- 高风险操作要人工确认，比如删除文件、改接口契约、改数据库 schema。
- 关键命令固定下来，比如 `pnpm lint`、`pnpm test`、`pnpm build`、类型检查、Playwright 回归。

**第三层：验证 Harness**

- 代码产出不能只看“能不能运行”，要有验证矩阵。
- 静态验证：Lint、TypeScript、格式化、依赖检查。
- 单测验证：核心函数、状态流转、边界条件。
- E2E 验证：关键用户路径，比如登录、支付、上传、生成任务。
- 视觉验证：复杂 UI 通过截图或浏览器检查布局是否异常。
- 人工 Review：重点看安全、性能、架构边界、业务语义是否正确。

**第四层：资产回归 Harness**

- 把有效 Prompt、检查清单、踩坑案例沉淀成项目级 Skill 或模板。
- 准备一批固定任务样本，用来回归 Prompt / Skill / 模型的质量。
- 记录每次任务的结果：一次通过率、人工修改量、失败原因、耗时、工具调用次数。
- 如果某个 Skill 更新后，同一批任务效果变差，就回滚或调整。
- 让团队从“个人会用 AI”升级成“团队有一套可复用的 AI 开发方法”。

可以把它理解成：Vibe Coding 解决“AI 帮我写”，Harness Engineering 解决“AI 怎么稳定、可控、可复用地写”。

### 实操口径

如果结合我自己的实践，我会拿“面经沉淀 Skill”举例。最开始只是临时让 AI 根据面试题生成回答，效果不稳定，后来我把它做成项目级 Skill：规定输入是公司、轮次、题目；输出必须有本轮考点、关键考点、实操口径、可背答案、注意点和可能追问；落文件时必须更新 `mianshi/README.md`；回答不能只背概念，要结合项目证据。这个 Skill 本身就是 Vibe Coding Harness 的一部分，因为它把 AI 的输入、输出、文件位置和质量标准都固定了。

如果换成代码开发，我会把 Harness 落成几件事：

- 需求进入 AI 前，先写任务规格和验收标准。
- AI 只能在指定模块内读写，不能顺手重构无关代码。
- 每次改动后必须跑固定验证命令。
- PR 描述里要求说明改了什么、怎么验证、有什么风险。
- 高频任务沉淀成 Skill，比如“支付渠道接入 Skill”“Next 水合问题排查 Skill”“组件性能优化 Skill”。
- 定期拿固定任务样本测试这些 Skill，观察一次通过率、返工率和失败原因。

### 可背答案

> 如果说的是 Vibe Coding 实践里的 Harness Engineering，我理解它不是一个普通测试工具，而是给 AI 编码建立工程护栏。因为 Vibe Coding 如果只是临时对话，很容易出现需求理解不稳定、改动范围失控、代码风格不一致、验证缺失这些问题。  
>   
> 我的做法会分四层：第一层是任务规格，把背景、目标、输入、涉及模块、禁止修改范围和验收标准写清楚；第二层是执行环境，限制 AI 能看的上下文、能改的文件和能执行的命令；第三层是验证 Harness，每次产出都要跑 Lint、类型检查、测试、构建或浏览器验证；第四层是资产回归，把稳定 Prompt、Checklist、Skill 和样例任务沉淀下来，后续模型或 Skill 变更时用同一批任务回归。  
>   
> 比如我现在做面经沉淀，不是每次临时让 AI 写答案，而是做成项目级 Skill，固定输入、输出结构、文件路径、索引更新和质量标准。代码开发也一样，高频任务会沉淀成 Skill，再用固定样本和验证命令保证它长期稳定。

### 面试现场更短版本

> 我会把它理解成 Vibe Coding 的工程化护栏：任务开始前有规格，执行过程中有限制，产出之后有验证，稳定经验再沉淀成 Skill。这样 AI 不是靠一次聊天发挥，而是进入团队研发流程。

### 注意点

- 不要把 Harness 说成“多写测试”，它更像 Vibe Coding 的过程控制和质量框架。
- 不要只讲 AI 工具名字，要讲任务规格、边界、验证、沉淀。
- 不要说“完全自动化”，团队里更合理的是低风险任务自动化，高风险任务人工 Review。
- 不要过度承诺“AI 产出确定”，更准确是通过 Harness 提高稳定性和可回归性。
