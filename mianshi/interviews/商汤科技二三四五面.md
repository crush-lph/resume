## 1. React 闭包陷阱

### 面试官想考什么

- 你是否真的理解函数组件“每次 render 都是新作用域”。
- 你是否知道 React 异步回调里为什么容易拿到旧 state。
- 你是否能给出可落地的修复方式，而不只是说“闭包问题”。

### 短答

React 闭包陷阱本质上是：函数组件每次渲染都会形成新的词法作用域，异步回调、定时器、事件监听器里捕获的是当次渲染时的 state / props，而不是“永远最新的值”。

### 详细分析

这个问题的根源有两层：

1. JavaScript 闭包会记住函数创建时所在的词法作用域。
2. React 函数组件每次渲染都会重新执行一遍函数，所以每次 render 都会产生新的 `state`、`props` 和局部变量绑定。

因此，如果你在某次 render 中创建了一个 `setTimeout`、`setInterval`、Promise 回调或事件监听器，这个回调拿到的是“那一次 render 时的值”，不是未来自动更新的值。

常见场景：

- 定时器里打印 state，结果永远是旧值。
- 异步请求回来后更新逻辑基于旧条件。
- 外部事件监听器里读到旧 props。

常见解法：

- 用函数式更新：`setCount((c) => c + 1)`。
- 在依赖变化时重新注册副作用。
- 用 `useRef` 保存最新值，让异步逻辑永远读 `ref.current`。

### 可背答案

> React 里的闭包陷阱本质上不是 React 独有问题，而是 JavaScript 闭包和函数组件渲染模型叠加的结果。函数组件每次 render 都会产生新的作用域，如果我在 `setTimeout`、`setInterval`、事件监听或异步回调里直接读取 state，就可能拿到旧值。常见解决方式有三种：第一，依赖更新时重新注册副作用；第二，用函数式 `setState`；第三，用 `useRef` 保存最新值，让异步逻辑始终读 ref。

### 示例

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  const countRef = useRef(count);

  useEffect(() => {
    countRef.current = count;
  }, [count]);

  useEffect(() => {
    const timer = setInterval(() => {
      console.log(countRef.current);
    }, 1000);

    return () => clearInterval(timer);
  }, []);

  return <button onClick={() => setCount((c) => c + 1)}>{count}</button>;
}
```

## 2. Promise 异步任务执行顺序

### 面试官想考什么

- 你是否区分同步代码、微任务、宏任务。
- 你是否能解释 `Promise.then` 为什么常常先于 `setTimeout`。
- 你是否能把顺序题说成稳定规则，而不是死记结果。

### 短答

同步代码先执行，当前宏任务执行完后会清空微任务队列，再进入下一轮宏任务。

### 详细分析

`Promise.then/catch/finally` 回调属于微任务。当前调用栈里的同步代码执行完后，不会立刻进入下一个 `setTimeout`，而是先清空当前轮次产生的所有微任务。

所以典型顺序是：

1. 执行同步代码。
2. 当前宏任务结束。
3. 清空微任务队列。
4. 浏览器视情况渲染。
5. 再取下一个宏任务。

你面试里可以顺手补一句：  
“Promise 题的本质不是背输出，而是先标同步、再标微任务、最后标宏任务。”

### 可背答案

> Promise 的 `then/catch/finally` 回调会进入微任务队列。JavaScript 执行顺序是：先执行当前调用栈里的同步代码；当前宏任务结束后，立刻清空微任务队列；然后浏览器再决定是否渲染；之后才会进入下一个宏任务，比如 `setTimeout`。所以很多题里 `Promise.then` 会先于 `setTimeout` 执行。

## 3. 浏览器事件循环

### 面试官想考什么

- 你是否理解浏览器如何协调 JS 执行和渲染。
- 你是否知道微任务为什么会影响页面卡顿。
- 你是否能把它和真实前端问题联系起来，比如流式渲染、长任务、输入卡顿。

### 短答

事件循环就是浏览器协调同步代码、微任务、宏任务和渲染时机的机制。

### 详细分析

浏览器不是一边跑 JS 一边随时渲染，而是按事件循环节奏推进。  
一个宏任务开始后，会先执行同步代码；同步代码执行完后，再把本轮产生的微任务全部执行完；然后浏览器才有机会做渲染和绘制。

这意味着：

- 微任务过多会推迟渲染。
- 一个超长同步任务会阻塞输入和动画。
- “页面卡”很多时候不是 React 慢，而是主线程被长任务占满。

所以很多优化思路，本质上都在做两件事：

- 减少长同步任务。
- 拆分低优先级工作，不要长期霸占主线程。

### 可背答案

> 浏览器事件循环的基本流程是：先执行一个宏任务里的同步代码，执行结束后清空微任务队列，然后浏览器有机会进行渲染，之后再从宏任务队列中取下一个任务继续执行。宏任务常见有 `setTimeout`、I/O、UI 事件回调；微任务常见有 `Promise.then`、`queueMicrotask`、MutationObserver。理解事件循环后，很多异步顺序题和渲染时机问题就能解释清楚。

## 4. Tree Shaking 的原理

### 面试官想考什么

- 你是否知道 Tree Shaking 不是“运行时优化”，而是构建阶段优化。
- 你是否知道它为什么依赖 ESM。
- 你是否知道为什么有时明明没用到代码，包里还是在。

### 短答

Tree Shaking 基于 ES Module 的静态结构分析，把未使用的导出在构建阶段删除。

### 详细分析

Tree Shaking 的前提是：构建工具能在编译时看清依赖关系。  
ESM 的 `import/export` 是静态声明，所以 bundler 可以分析“哪些导出被用了，哪些没被用”。没被用的部分就可以在打包时去掉。

为什么 CommonJS 效果差？  
因为 `require()` 是运行时执行的，依赖关系不够静态，构建器很难安全判断哪些代码一定没用。

为什么有时 Tree Shaking 不生效？

- 包是 CommonJS。
- 存在副作用导入。
- `package.json` 的 `sideEffects` 没标对。
- 代码写法让构建器无法安全删除。

### 可背答案

> Tree Shaking 的核心前提是 ES Module 的 import / export 在编译时可静态分析。构建工具可以知道某个导出是否被使用，如果没有被引用，就在打包阶段去掉这部分代码。它对 CommonJS 效果较差，因为 `require` 是运行时执行，依赖关系不够静态。实际项目里还要注意副作用文件，如果一个包在 `package.json` 里没正确标注 `sideEffects`，Tree Shaking 可能不彻底。

## 5. 客户端组件为什么会在服务端执行

### 面试官想考什么

- 你是否真正理解 Next.js App Router 的渲染模型。
- 你是否知道 `'use client'` 的语义边界。
- 你是否能解释为什么客户端组件里直接用 `window` 会报错。

### 短答

在 Next.js App Router 里，`'use client'` 不是“只在浏览器运行”，而是“以客户端组件身份参与渲染和 hydration”，首次请求时它的渲染逻辑仍然可能参与服务端预渲染。

### 详细分析

`'use client'` 解决的是“这个组件是否能使用客户端能力”，比如：

- `useState`
- `useEffect`
- 浏览器 API
- 事件处理

但这不代表它的函数体永远不会出现在服务端执行链路中。  
在 SSR 场景下，Next.js 为了输出首屏 HTML，仍然可能让客户端组件参与预渲染过程。

真正的边界是：

- render 逻辑有机会参与服务端输出；
- 浏览器副作用逻辑只能在客户端执行。

所以安全写法是：

- 浏览器 API 放在 `useEffect` 里；
- 或做 `typeof window !== 'undefined'` 判断；
- 或者对必须纯客户端的组件使用 `dynamic(..., { ssr: false })`。

### 可背答案

> 很多人误以为客户端组件只会在浏览器执行，其实不是。Next.js 的客户端组件主要是说它可以使用 state、effect、浏览器 API，并最终在客户端完成 hydration 和交互。但在 SSR 场景里，为了生成初始 HTML，客户端组件的渲染函数也可能在服务端参与预渲染。真正不能在服务端执行的是依赖浏览器环境的副作用逻辑，比如 `window`、`document`、`localStorage`，这些应该放在 `useEffect` 里或者做环境判断。

## 6. Next 水合错误的根本原因是什么

### 面试官想考什么

- 你是否知道水合不是“渲染报错”，而是“服务端和客户端首屏结果对不上”。
- 你是否能从根因角度解释，而不是只说“用了 window”。
- 你是否知道怎么系统排查。

### 短答

服务端生成的 HTML 和客户端首次渲染结果不一致。

### 详细分析

Hydration 的本质是：React 在浏览器里接管服务端已经输出好的 HTML。  
如果客户端第一次 render 出来的结果和服务端 HTML 不一致，React 就会报 hydration mismatch。

常见根因：

- render 阶段使用不稳定值：`Date.now()`、`Math.random()`。
- render 阶段直接访问浏览器环境：`window`、`document`、`localStorage`。
- 根据屏幕宽度、时区、语言、用户环境做了分支渲染。
- 服务端数据和客户端初始化数据不一致。
- 非法 DOM 结构嵌套。

排查顺序：

1. 先看首屏 render 是否依赖浏览器环境。
2. 再看是否有随机值、时间值。
3. 再看服务端和客户端数据源是否一致。
4. 最后检查 DOM 结构和第三方组件。

### 可背答案

> Next 水合错误的根本原因，是服务端输出的 HTML 结构和客户端首次 render 出来的虚拟 DOM 结果不一致，React 在 hydration 时发现两边对不上。常见原因包括：直接使用 `window`、`document`、`localStorage`；在 render 阶段使用 `Date.now()`、`Math.random()`；依赖浏览器尺寸或用户环境；服务端和客户端数据源不一致；或者非法的 DOM 嵌套结构。解决思路是保证首屏 render 结果确定且一致，把浏览器相关逻辑放到 `useEffect`，以及让服务端和客户端使用同一份初始数据。

## 7. Next 接口怎么写

### 面试官想考什么

- 你是否知道 Next.js 不只是做页面，也能做服务端接口。
- 你是否知道 App Router 时代接口文件怎么组织。
- 你是否知道什么场景适合放在 Next 接口层做 BFF。

### 短答

常见有两种：Pages Router 用 `pages/api`，App Router 用 `app/api/.../route.ts`。

### 示例

```ts
// app/api/user/route.ts
import { NextResponse } from "next/server";

export async function GET() {
  return NextResponse.json({
    code: 0,
    data: {
      name: "lipenghu",
    },
  });
}
```

### 可背答案

> 在 Next.js App Router 里，接口通常写在 `app/api/**/route.ts`。不同 HTTP 方法导出不同函数，比如 `GET`、`POST`。如果涉及 cookie、header、鉴权和服务端能力，这种方式比较方便，因为它天然运行在服务端。对于 BFF 场景，也可以在这里做接口聚合、字段裁剪和鉴权兜底。

### 详细分析

Next 接口层常见价值：

- 聚合多个后端接口，减少前端多次请求。
- 屏蔽后端字段细节，给前端更稳定的数据结构。
- 处理 cookie、token、header、签名、灰度标识。
- 隔离第三方服务密钥，避免暴露到浏览器。

所以面试里如果被追问“为什么不用前端直接请求后端”，你可以答：  
“如果只是简单透传，直连也可以；但只要涉及鉴权、聚合、裁剪、签名、安全和 SSR 上下文，BFF 会更合适。”

## 8. 前端水印怎么做

### 面试官想考什么

- 你是否做过前端防泄漏手段。
- 你是否知道水印的本质是“追责”和“提高泄漏成本”，不是绝对安全。

### 短答

常见做法是生成平铺半透明水印层，叠在页面上方；内容可包含用户名、时间、部门、ID 等。

### 详细分析

水印常见实现：

- Canvas 先画出文字，再导出为 base64，当作背景图平铺。
- SVG 动态生成，适合矢量文字和缩放。
- 直接用 DOM 层平铺文本。

一般水印信息包括：

- 用户名 / 工号
- 时间戳
- 部门 / 角色
- 会话 ID / 追踪信息

设计目标通常不是“防截图”，而是：

- 增加传播成本
- 提高追责能力
- 对敏感页面形成心理威慑

### 方案

- Canvas 生成 base64 水印图，作为背景平铺。
- 绝对定位 DOM 水印层。
- SVG 水印。

### 示例思路

```txt
创建一个 fixed 的 overlay
pointer-events: none
background-image 使用 canvas 生成的 dataURL
z-index 足够高
```

## 9. 前端如何阻止水印的去除

### 面试官想考什么

- 你是否知道前端安全能力的边界。
- 你会不会不切实际地说“前端可以彻底防删除”。

### 短答

前端无法绝对阻止，只能提高篡改成本。

### 详细分析

因为代码和 DOM 都在用户浏览器里，用户总能通过 DevTools、脚本注入、截图裁剪等方式绕过前端水印。  
所以正确回答不是“防得住”，而是“尽量提高攻击成本”。

常见策略：

- MutationObserver 监听节点删除后重建。
- 多层水印，分散在不同容器。
- 随机偏移、随机透明度。
- 把水印绘制进 canvas、图片或视频帧。
- 服务端下发带水印素材。

### 可背答案

> 前端水印本质上运行在用户浏览器里，所以没法做到绝对防删除。能做的是提高去除成本，比如多层水印、随机偏移、MutationObserver 监听节点删除后自动恢复、把水印绘制在 canvas 或视频流上、服务端返回带水印图片等。真正敏感场景还是要结合权限、审计、截图追责和后端策略，不能把安全全押在前端。

## 10. 一键换肤怎么做

### 面试官想考什么

- 你是否理解主题系统不是改几个颜色，而是设计 token 体系。
- 你是否能讲出工程化方案，而不是只说“切 className”。

### 短答

核心是把颜色、字体、间距等样式抽成设计 token，再通过 CSS Variables、主题 class 或配置中心统一切换。

### 详细分析

换肤通常分三层：

1. 设计 token：主色、文字色、背景色、边框色、阴影、圆角、间距。
2. 主题实现：CSS Variables、CSS-in-JS theme、组件库主题能力。
3. 切换机制：切换 class、动态注入变量、从配置中心拉主题。

关键点：

- 组件不能写死颜色。
- 主题值要可持久化，比如 localStorage 或用户配置。
- 要考虑首屏闪烁问题，最好在应用初始化早期注入主题。

### 可背答案

> 一键换肤本质上是把主题从具体样式值抽象成 token，比如主色、文字色、背景色、边框色。实现上通常会用 CSS Variables：默认主题挂在 `:root`，切换主题时给 `html` 或 `body` 加 theme class，覆盖不同变量值，组件只消费变量，不直接写死颜色。如果项目使用 antd、Tailwind 或 CSS-in-JS，还可以结合它们的主题能力。关键点是样式 token 化、组件不写死值、主题切换持久化。

## 11. 无感刷新 token

### 面试官想考什么

- 你是否做过完整鉴权链路。
- 你是否知道 token 刷新里的并发问题。
- 你是否知道安全边界，而不是只会写个 401 重试。

### 短答

用 access token + refresh token。access token 短期有效，请求失败且命中过期场景时，自动用 refresh token 换新 token，然后重放原请求。

### 详细分析

完整链路一般是：

1. 正常请求带 access token。
2. 服务端发现 token 过期，返回 401 或约定错误码。
3. 前端进入刷新流程，用 refresh token 换新 access token。
4. 刷新成功后重放原请求。
5. 刷新失败则清理登录态并跳转登录页。

真正的难点是并发：

- 如果 10 个请求同时 401，不能让 10 个请求都去刷新。
- 正确做法是设置刷新锁，只发一个 refresh 请求。
- 其他请求进入等待队列，等刷新成功后统一重放。

还要注意：

- refresh token 自身也可能过期。
- 刷新失败要防止死循环重试。
- 敏感 token 存储位置要结合安全要求设计。

### 可背答案

> 无感刷新 token 的核心是双 token 机制。access token 用于正常请求，生命周期较短；refresh token 生命周期更长，用于在 access token 过期时获取新的 access token。前端一般在请求拦截器或响应拦截器里处理 401 或约定的过期码，但要注意并发场景：多个请求同时过期时，不能让每个请求都去刷新一次，而是要做刷新锁和请求队列，保证同一时刻只发一个刷新请求，成功后重放队列中的原请求。

## 12. 单点登录 SSO

### 面试官想考什么

- 你是否理解“认证中心”和“业务系统”的职责分离。
- 你是否知道前端在 SSO 里的真实工作是什么。
- 你是否能意识到跨域和 cookie 安全问题。

### 短答

SSO 是多个系统共享同一套登录态，用户在一个系统登录后，访问其他系统无需再次登录。

### 详细分析

SSO 的核心不是“共享 localStorage”，而是：

- 认证中心统一认证；
- 业务系统信任认证中心发出的结果。

前端常见职责：

- 未登录时跳转到统一登录中心。
- 处理回跳后的 code / ticket。
- 调业务后端换取用户态。
- 维护退出登录联动。

跨系统时还要考虑：

- 主域 / 子域 cookie
- SameSite
- 跨站重定向
- token 不能随便暴露在 URL

### 可背答案

> 单点登录的核心是“认证中心统一认证，业务系统信任认证结果”。常见做法是用户先跳到统一认证中心登录，认证成功后拿到票据或 code，业务系统再通过后端去认证中心换取用户信息和会话。前端主要负责跳转、回调参数处理、登录态恢复和退出联动。跨域场景下还要考虑 cookie 域、SameSite、token 传递和安全策略。

## 13. 请求多次调用的时候，实际只发起一个请求

### 面试官想考什么

- 你是否知道请求去重和缓存的区别。
- 你是否能写出简单可用的去重方案。
- 你是否知道这类能力在 React Query / SWR 里已有成熟实现。

### 短答

这叫请求合并 / 请求去重。

### 详细分析

请求去重适合“同一时刻、同一资源、同一参数”的请求。  
它不是长期缓存，而是短时间内复用同一个进行中的 Promise。

实现要点：

- 为请求生成唯一 key。
- 如果 key 已存在 pending 请求，直接返回同一个 Promise。
- 请求结束后删除 key。

适合场景：

- 页面多个组件同时请求同一份用户信息。
- 多次点击触发相同详情请求。
- 页面初始化时多个模块依赖相同配置数据。

### 可背答案

> 如果同一时刻多个地方请求同一个资源，没必要重复发请求。常见做法是用一个 Map 记录进行中的 Promise，请求发起前先根据 key 判断有没有相同请求在 pending，如果有就直接复用这个 Promise；等请求完成后再删除缓存。React Query、SWR 这类库本身也内置了请求去重和缓存机制。

### 示例

```ts
const pendingMap = new Map<string, Promise<any>>();

function requestOnce(key: string, fn: () => Promise<any>) {
  if (pendingMap.has(key)) {
    return pendingMap.get(key)!;
  }

  const task = fn().finally(() => {
    pendingMap.delete(key);
  });

  pendingMap.set(key, task);
  return task;
}
```

## 14. 点击下拉区域外才能关闭下拉弹窗

### 面试官想考什么

- 你是否掌握基础交互实现。
- 你是否能正确处理事件绑定和清理。
- 你是否知道 portal、冒泡和层级情况下的边界问题。

### 短答

本质是“点击外部关闭”，常用 document 监听 + ref 判断。

### 详细分析

核心思路是：

- 给弹层主体一个 ref。
- 在 document 上监听 `mousedown` 或 `click`。
- 判断当前点击目标是否在 ref 容器内。
- 不在则关闭。

注意边界：

- 组件卸载时移除监听器。
- 如果弹层通过 portal 渲染，要确保 ref 指向真实弹层根节点。
- 有些场景 `mousedown` 比 `click` 更稳，因为它更早触发。

### 示例

```tsx
function Dropdown() {
  const ref = useRef<HTMLDivElement>(null);
  const [open, setOpen] = useState(false);

  useEffect(() => {
    function handleClick(event: MouseEvent) {
      if (!ref.current?.contains(event.target as Node)) {
        setOpen(false);
      }
    }

    document.addEventListener("mousedown", handleClick);
    return () => document.removeEventListener("mousedown", handleClick);
  }, []);

  return <div ref={ref}>{open && <div>menu</div>}</div>;
}
```

## 17. 扫码登录怎么实现

### 面试官想考什么

- 你是否理解 PC 与移动端协同登录流程。
- 你是否知道状态同步怎么做。
- 你是否知道二维码安全边界。

### 短答

PC 端生成二维码，二维码关联一次性登录凭证；移动端扫码确认后，服务端更新状态；PC 端通过轮询、SSE 或 WebSocket 感知登录成功。

### 详细分析

扫码登录本质是“跨设备确认登录”。  
PC 不知道用户是谁，所以先向服务端申请一个短期场景 ID；移动端已经有登录态，扫码后相当于“代用户确认把这个 PC 场景授权登录”。

关键点：

- 二维码短时有效。
- 一次性使用，避免重放。
- PC 端状态更新可以轮询，也可以走 WebSocket / SSE。
- 用户取消、过期、重复扫码都要有清晰状态提示。

### 可背答案

> 扫码登录一般分三步。第一步，PC 端请求服务端生成二维码，二维码里包含一次性 token 或场景 ID。第二步，移动端扫码后完成登录确认，服务端把该场景标记为已确认。第三步，PC 端通过轮询、SSE 或 WebSocket 监听状态变化，拿到成功信号后建立登录态。关键点是二维码要短时有效、一次性使用，避免重放，还要处理取消、过期和重复扫码。

## 18. pnpm、npm、yarn 的区别，pnpm 的优势是什么

### 面试官想考什么

- 你是否只会用命令，还是理解依赖安装模型。
- 你是否懂 monorepo 场景下为什么很多团队偏爱 pnpm。

### 短答

三者都是包管理器；pnpm 的核心优势是磁盘复用、高效安装、依赖隔离更严格。

### 详细分析

核心差异不在“都能 install”，而在：

- 包怎么存储。
- node_modules 怎么组织。
- 依赖隔离是否严格。

pnpm 的优势：

- 全局 store 复用包内容，节省磁盘。
- 安装更快。
- 依赖边界更严格，减少幽灵依赖。
- 更适合 monorepo。

面试里加分的一句是：  
“pnpm 最大的工程价值不只是速度，而是让依赖关系更真实，能尽早暴露子包没声明依赖的问题。”

>
> 另外 pnpm 的 node_modules 结构更严格，不容易产生幽灵依赖，这对 monorepo 和大型团队是优势，因为能逼着子包显式声明自己真正依赖的包，提高依赖边界清晰度。

## 19. React 中怎么实现 keep-alive

### 面试官想考什么

- 你是否理解 keep-alive 的本质不是“缓存数据”，而是“缓存页面实例和状态”。
- 你是否能讲出适用场景和风险。

### 短答

核心是“组件切走时不卸载，而是缓存实例和状态，切回来时直接恢复”。

### 详细分析

keep-alive 适用于：

- 后台系统列表页切详情再回来。
- 表单填写中途切页再回来。
- 保留滚动位置、筛选条件、局部 UI 状态。

它的本质不是请求缓存，而是避免组件卸载。  
常见做法是放入缓存容器，切换时隐藏而不卸载；恢复时直接显示旧实例。

注意风险：

- 缓存太多会占内存。
- 需要失效策略。
- 某些页面切回来后数据可能需要主动刷新，而不是永远用旧状态。

### 方案

- 路由级缓存组件。
- 利用 React 节点缓存容器。
- 使用现成库，如 `react-activation`。
- 自定义缓存 key + 显隐切换。

### 可背答案

> React 本身没有内置 Vue 那样的 keep-alive，但可以通过缓存组件实例或 DOM 节点来实现。常见做法是把页面挂在一个缓存容器里，切换路由时不卸载，只是隐藏；回来时再显示。项目里通常会配合路由 key、缓存白名单、最大缓存数和手动失效策略使用。对于后台系统，这能保留列表筛选、滚动位置和表单输入状态。

## 23. 浏览器为什么要做请求并发数量限制

### 面试官想考什么

- 你是否知道网络资源不是无限的。

为了避免单个站点占满网络资源，影响公平性、稳定性和浏览器调度。

- 避免首屏发太多低价值请求

> 浏览器限制同域并发请求数，核心是为了平衡网络资源、避免连接过多带来的拥塞和性能问题。HTTP/1.1 时代这个限制更明显，因为每个连接成本更高；HTTP/2 通过多路复用缓解了问题，但浏览器和服务端仍然会做连接和流量控制。对前端来说，这意味着不能无脑并发几十上百个请求，应该做资源合并、懒加载、优先级控制和请求调度。

- 你是否理解前端工程不是写完代码就结束。
- 你是否知道构建、发布、回滚、监控这些上线链路。

### 可背答案

> 前端部署流程通常包括：代码提交 -> CI 安装依赖和跑测试 -> 构建产物 -> 上传到对象存储或部署平台 -> 刷新 CDN / 更新容器 -> 灰度验证 -> 监控回看。
>
> 如果是 Next.js，还要区分静态资源、SSR 服务和环境变量配置；如果是纯静态站点，通常发布到 CDN 或对象存储即可。比较成熟的流程还会包含版本号、回滚机制、预发环境验证、变更记录和报警。

### 详细分析

如果要讲完整，可以拆成：

- 开发提交：分支、PR、Review。
- CI：安装依赖、Lint、测试、构建。
- 发布：上传静态资源、部署 SSR 服务、更新环境变量。
- 验证：预发、灰度、冒烟测试。
- 观察：错误监控、性能指标、业务指标。
- 回滚：版本回退、静态资源回切、服务降级。

## 27. React 和 Next 有什么区别

### 面试官想考什么

- 你是否清楚“库”和“框架”的边界。
- 你是否知道为什么项目里会从 React 裸栈升级到 Next。

### 短答

React 是 UI 库，Next.js 是基于 React 的全栈框架。

### 详细分析

React 解决的是：

- 组件化
- 状态驱动视图
- Hooks

Next.js 在 React 之上补齐的是：

- 文件路由
- SSR / SSG / ISR
- 服务端组件与接口
- 图片优化
- Metadata
- 缓存和数据获取策略

所以 React 更偏基础能力，Next 更偏工程化落地。

### 可背答案

> React 主要解决组件化 UI 构建和状态驱动视图更新问题，本身不内置路由、SSR、文件路由、接口层、构建规范等；Next.js 是基于 React 的框架，补齐了 SSR / SSG / ISR、文件路由、服务端能力、接口路由、数据获取、图片优化、Metadata、缓存等一整套工程化能力。所以 React 更像基础能力，Next.js 更像适合中大型项目的完整框架方案。

## 29. forEach 的时候直接修改 item，原数组会变吗

### 面试官想考什么

- 你是否理解值类型和引用类型。
- 你是否知道 `forEach` 回调参数修改和原数组元素修改的区别。

### 短答

要看数组元素是基本类型还是引用类型。

### 详细分析

本质区别在于：

- 如果元素是对象，`item` 拿到的是对象引用，修改对象内部属性会影响原数组。
- 如果元素是 number / string / boolean，回调参数只是值拷贝，重新赋值不会回写数组。

### 可背答案

> 如果数组里是对象，`forEach` 里直接改 `item.xxx`，原数组会变，因为 `item` 指向的是同一个对象引用；如果是基本类型，比如 number、string，直接给 `item` 重新赋值不会影响原数组，因为只是修改了回调参数本身，不会写回数组。

### 示例

```ts
const arr1 = [{ count: 1 }];
arr1.forEach((item) => {
  item.count = 2;
});
console.log(arr1[0].count); // 2

const arr2 = [1, 2, 3];
arr2.forEach((item) => {
  item = item + 1;
});
console.log(arr2); // [1, 2, 3]
```

## 复习优先级

- React 闭包陷阱。
- Promise / 事件循环。

第二优先级：

- Tree Shaking。
- 请求去重。
- keep-alive。
- React 18 新特性。
- 用户为中心性能指标。

第三优先级：

- 水印、一键换肤、字体加载。
- 部署流程。
- pnpm / npm / yarn 对比。
- Vibe Coding 与模型选型。
