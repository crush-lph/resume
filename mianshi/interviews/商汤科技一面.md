## 1. 闭包是什么，有哪些应用场景，有什么缺陷

### 回答主线

闭包是函数和其词法作用域的组合。即使外层函数执行结束，内部函数仍然可以访问外层函数中的变量。

### 可背答案

> 闭包可以理解成“函数记住了它创建时的词法作用域”。当一个内部函数引用了外部函数的变量，并且这个内部函数在外部函数执行结束后仍然被使用，那么这些被引用的变量不会被释放，这就是闭包。  
>  
> 常见应用包括封装私有变量、函数柯里化、防抖节流、缓存结果、事件回调中保存上下文、React Hooks 中函数捕获状态等。它的缺陷是如果长期持有不再需要的变量，可能造成内存不能及时释放；另外在异步回调或循环中，如果不理解闭包捕获的是变量引用，也容易拿到非预期的值。

### 应用场景

- 私有变量封装。
- 防抖、节流。
- 函数柯里化。
- 缓存和 memoize。
- 事件监听、异步回调中保存上下文。
- React Hooks 中函数捕获组件状态。

### 易错点

- 闭包不是“函数里面套函数”这么简单，关键是内部函数引用外部词法作用域。
- 闭包不是一定会导致内存泄漏，只有长期持有无用引用时才可能产生问题。
- React 中要注意 stale closure，例如定时器、事件监听里拿到旧 state。

## 2. 防抖节流是什么，有什么区别，应用场景

### 回答主线

防抖是“等用户停止触发一段时间后再执行”，节流是“固定时间内最多执行一次”。

### 可背答案

> 防抖和节流都是控制高频事件执行频率的手段。防抖强调最后一次触发，适合输入框搜索、窗口 resize 后重新计算布局、表单校验等场景；节流强调固定频率执行，适合滚动监听、拖拽、页面曝光统计、滚动加载等场景。  
>  
> 比如搜索框输入时，我希望用户停下来 300ms 后再请求接口，这适合防抖；滚动页面时，我希望每 200ms 计算一次滚动位置，而不是每个 scroll 事件都执行，这适合节流。

### 区别

| 维度 | 防抖 debounce | 节流 throttle |
|---|---|---|
| 核心 | 停止触发后执行 | 固定频率执行 |
| 关注点 | 最后一次 | 过程中的间隔 |
| 场景 | 搜索、校验、resize | scroll、drag、曝光、进度同步 |

### 易错点

- 防抖不是减少请求次数的唯一方案，复杂搜索还要处理请求取消和竞态。
- 节流不是完全实时，间隔过大会影响体验，间隔过小优化不明显。

## 3. 浏览器缓存

### 回答主线

浏览器缓存主要分为强缓存和协商缓存。强缓存不发请求，协商缓存会向服务器确认资源是否变化。

### 可背答案

> 浏览器缓存可以分成强缓存和协商缓存。强缓存主要看 `Cache-Control` 和 `Expires`，如果命中，浏览器直接使用本地缓存，不会请求服务器。协商缓存主要看 `ETag / If-None-Match` 和 `Last-Modified / If-Modified-Since`，浏览器会请求服务器确认资源是否变化，如果没变化返回 304，继续使用本地缓存。  
>  
> 实际项目里，通常会对带 hash 的静态资源设置长缓存，例如 JS、CSS、图片；对 HTML 或需要及时更新的数据设置短缓存或 no-cache；接口缓存则要结合业务实时性、用户态和权限来设计。

### 项目表达

> 在 Next.js 项目里，我会区分静态资源、页面 HTML、接口数据和 SEO 页面。静态资源走文件 hash + 长缓存；动态页面和用户态接口不盲目缓存；SEO 内容页可以根据内容更新频率做服务端缓存或 ISR，避免每次都实时计算。

### 易错点

- `no-cache` 不是不缓存，而是使用前要协商确认。
- `no-store` 才是不存储缓存。
- 用户相关接口不要随意公共缓存，避免数据串号。

## 4. React 的并发渲染是什么

### 回答主线

React 并发渲染不是多线程，而是 React 18 基于 Fiber 的可中断、可恢复、可丢弃、可按优先级调度的渲染机制。

### 可背答案

> React 并发渲染的核心是让 React 在 render 阶段具备调度能力。它可以把一次大的渲染任务拆成多个小任务，在必要时暂停低优先级更新，优先响应用户输入等高优先级任务，从而减少页面卡顿。  
>  
> 它不是多线程，React 仍然主要运行在 JS 主线程上。并发能力主要影响 render 阶段，commit 阶段仍然是同步且不可中断的。常见 API 有 `startTransition`、`useTransition`、`useDeferredValue` 和 `Suspense`。比如搜索场景里，输入框更新是高优先级，列表筛选结果可以放到 transition 里作为低优先级更新。

### 示例

```tsx
import { startTransition, useState } from 'react';

function SearchPage() {
  const [keyword, setKeyword] = useState('');
  const [query, setQuery] = useState('');

  const handleChange = (value: string) => {
    setKeyword(value);

    startTransition(() => {
      setQuery(value);
    });
  };

  return (
    <>
      <input value={keyword} onChange={(event) => handleChange(event.target.value)} />
      <SearchResult query={query} />
    </>
  );
}
```

### 易错点

- 并发渲染不是 Web Worker，也不是多线程。
- `startTransition` 不是防抖，它只是降低更新优先级。
- render 阶段可能执行多次，所以不要在 render 里写副作用。

## 5. 响应式怎么做

### 回答主线

响应式不是只写媒体查询，而是布局、尺寸、图片、组件形态和交互方式一起适配。

### 可背答案

> 响应式设计我一般从几个层面做。布局上使用 Flex/Grid、百分比、`minmax`、`clamp` 等方式减少写死宽度；断点上用媒体查询或 Tailwind 的响应式前缀处理不同屏幕；图片用 `srcset`、`sizes` 或 Next.js Image 做多尺寸适配；复杂组件在移动端可能改变交互形态，比如表格改卡片、侧边栏改抽屉。  
>  
> 同时要注意触摸区域、字体可读性、横向滚动、弹窗高度、虚拟键盘遮挡等移动端体验问题。

### 项目表达

> 在跨境 SaaS 或数据平台里，我不会简单把 PC 页面缩小，而是会根据核心操作重新组织信息层级。比如筛选区在 PC 上横向展开，在移动端收敛成抽屉；复杂表格移动端只展示关键字段，详情进入二级页。

## 6. Tailwind 使用

### 回答主线

Tailwind 是 utility-first CSS 框架，用原子类快速组合样式，适合组件化开发和设计规范约束。

### 可背答案

> Tailwind 的优势是开发效率高、样式和组件结构靠得近、天然支持响应式和主题配置。比如 `md:grid-cols-2`、`lg:grid-cols-4` 可以快速处理断点。项目里我会通过 `tailwind.config` 统一颜色、间距、字体、断点，避免团队随意写值。  
>  
> 但 Tailwind 也有缺点，比如 className 可能很长，复杂条件样式可读性下降。所以我会配合 `clsx`、`tailwind-merge` 或组件封装，把重复样式收敛起来。对于高度复用的 UI，还是要抽组件，而不是每个页面复制一长串 class。

### 易错点

- Tailwind 不是不用设计规范，而是把设计 token 放进配置。
- 不要在项目里大量使用任意值，例如 `w-[317px]`，否则会破坏一致性。

## 7. SEO 优化做了什么事情

### 回答主线

结合 FastMoss：SSR、动态 Metadata、Blog 内容体系、结构化内容、内链、sitemap、robots、多语言 SEO、性能优化、监控验证。

### 可背答案

> 在 FastMoss 里 SEO 不是单点优化，而是一套组合方案。技术上先通过 Next.js SSR 提升搜索引擎可抓取性；然后为核心页面生成动态 title、description、canonical、Open Graph 等元数据；内容上搭建 Blog 和结构化内容体系，围绕业务关键词生产可索引页面；站内结构上优化内链、sitemap 和 robots，让搜索引擎更容易发现和理解页面。  
>  
> 多语言场景下还要处理 locale URL、canonical、hreflang 和重复内容问题。性能上也会优化 LCP、首屏资源和移动端体验，因为页面体验也会影响 SEO 效果。最后通过 Search Console 或站长平台看收录、曝光、点击和索引状态，避免只凭感觉判断。

### 项目亮点表达

> 我们通过 SSR、动态 Metadata、Blog 内容体系、结构化内容和内链优化，将 SEO 收录量从 10W+ 提升到 500W+，支撑自然流量增长。

## 8. 动态元数据和缓存怎么做

### 回答主线

动态元数据解决“不同页面有不同 SEO 信息”，缓存解决“内容页不必每次实时计算，同时又能更新”。

### 可背答案

> 在 Next.js 里，动态元数据可以通过 `generateMetadata` 根据路由参数、语言、业务数据生成 title、description、canonical、Open Graph 等信息。比如商品详情、达人详情、Blog 文章都不能共用一套静态 meta，需要根据页面内容动态生成。  
>  
> 缓存上要按页面类型区分：高频变化的用户态页面不缓存或短缓存；SEO 内容页、Blog、详情页可以用服务端缓存、fetch 缓存或 ISR，根据内容更新频率设置 revalidate。静态资源使用 hash + 长缓存。核心原则是：既保证搜索引擎看到稳定内容，又避免用户看到过期或串号的数据。

### 示例

```ts
export async function generateMetadata({ params }: PageProps) {
  const article = await getArticle(params.slug);

  return {
    title: `${article.title} | FastMoss`,
    description: article.summary,
    alternates: {
      canonical: `https://www.fastmoss.com/blog/${params.slug}`,
    },
    openGraph: {
      title: article.title,
      description: article.summary,
      images: [article.coverUrl],
    },
  };
}
```

```ts
const article = await fetch(`/api/articles/${slug}`, {
  next: {
    revalidate: 3600,
  },
});
```

### 易错点

- 用户态数据不要随意做公共缓存。
- 动态 meta 依赖的数据要稳定，不能接口失败就生成空 title。
- canonical、hreflang、多语言 URL 要统一，否则容易重复收录。

## 9. 场景题：有一个上万行代码的 React 组件，怎么优化

### 回答主线

先止血，再拆分，再治理状态和性能，最后补测试和文档。不要一上来重写。

### 可背答案

> 我会先判断这个上万行组件的问题是可维护性、性能，还是两者都有。第一步先做保护：补关键路径测试，梳理组件输入输出、接口调用、状态流转和副作用，避免重构破坏功能。  
>  
> 第二步按职责拆分，比如 UI 展示、表单逻辑、数据请求、权限判断、弹窗、表格、图表、埋点分别拆成子组件、Hook 或 service。第三步治理状态，把局部 UI 状态留在组件内，服务端数据交给 React Query，全局共享状态放到 Zustand 或 Context，避免一个组件里堆几十个 state。  
>  
> 如果还有性能问题，再用 React DevTools Profiler 定位重复渲染、重计算和大列表问题，针对性使用 `memo`、`useMemo`、`useCallback`、虚拟列表、懒加载和拆包。最后通过测试、Code Review 和文档把边界固化下来。

### 拆分方向

- UI 展示组件。
- 业务容器组件。
- 数据请求 service。
- 自定义 Hook。
- 表单 schema 和校验。
- 权限与埋点逻辑。
- 弹窗、表格、图表等独立模块。

### 易错点

- 不要为了拆而拆，先识别变化点和职责边界。
- 不要一上来全量重写，风险太大。
- `useMemo` 和 `memo` 不是万能，先用 Profiler 定位。

## 10. React 中怎么做状态管理

### 回答主线

状态管理要先分类，不是所有状态都进全局 store。

### 可背答案

> React 状态管理我会按状态类型拆。局部 UI 状态，比如弹窗开关、输入框、tab，直接用 `useState` 或 `useReducer`。跨组件共享状态，比如用户信息、权限、语言、主题、支付状态，可以用 Zustand、Redux 或 Context。服务端状态，比如列表、详情、分页、缓存、重新请求，优先用 React Query 或 SWR 管理。  
>  
> 我不建议把接口数据全部塞进全局 store，因为这样会自己处理缓存、过期、loading、错误、竞态和重新请求，复杂度很高。合理做法是服务端状态交给专门的库，全局 store 只保存真正需要跨页面共享的客户端状态。

### 项目表达

> 在 FastMoss 里，用户态、权限、支付态这类跨页面状态适合放 store；列表筛选、详情接口这类服务端状态更适合通过请求层或缓存库管理；组件内部交互状态保留在本地，避免全局状态膨胀。

### 易错点

- Context 适合低频全局状态，不适合高频更新的大量数据。
- Redux / Zustand 解决客户端状态，不天然解决接口缓存。
- 状态越全局，修改影响面越大。

## 11. Vibe Coding 可复用资产怎么沉淀，有哪些

### 回答主线

不要只说“用了 AI 工具”，要说把 AI 提效沉淀成团队资产：Prompt 模板、Skill、Checklist、代码模板、知识库、评审规范、脚手架。

### 可背答案

> Vibe Coding 在团队里不能只停留在个人随手问 AI，而要沉淀成可复用资产。我们会把高频任务整理成 Prompt 模板，比如需求拆解、接口联调、组件生成、Code Review、自测清单、Bug 定位、PR 描述。对于更稳定的流程，可以沉淀成 Skill，比如简历优化 Skill、前端页面开发 Skill、代码审查 Skill、支付接入 Skill，让 AI 每次按固定流程和约束执行。  
>  
> 除了 Prompt 和 Skill，还可以沉淀代码模板、组件模板、Hook 模板、接口 service 模板、错误处理规范、测试用例模板和项目知识库。这样 AI 输出会更贴近项目，而不是每个人各问各的，导致风格和质量不一致。

### 可复用资产清单

- Prompt 模板：需求拆解、方案评审、代码生成、重构、测试、Review、线上问题排查。
- Skill：前端开发规范、React 最佳实践、支付渠道接入、SEO 检查、简历优化、PPT/文档生成。
- Checklist：SSR 检查、权限检查、支付链路检查、SEO 检查、性能检查、安全检查。
- 代码模板：组件模板、Hook 模板、service 模板、状态管理模板、错误边界模板。
- 知识库：项目架构、接口规范、业务术语、常见问题、踩坑记录。
- 自动化：脚手架、Lint 规则、测试生成、PR 描述生成、变更影响分析。

### 面试加分表达

> 我理解 Vibe Coding 的团队价值不只是让个人写代码更快，而是把经验转成可复用资产。Prompt 解决一次性任务的表达效率，Skill 解决稳定流程的执行一致性，Checklist 解决质量底线，代码模板解决工程一致性。这样 AI 才能从个人工具变成团队工程能力。
