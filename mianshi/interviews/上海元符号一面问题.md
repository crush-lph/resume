## 3. 为什么从 Umi 转向 Next.js

### 你的回答问题

- 你提到了 SEO 和 Umi 灵活性不足，方向正确。
- 但可以讲得更像“业务决策链”，而不是“框架不够灵活所以换”。

### 正确思路

核心是：业务增长目标 -> 公开页 SEO 和首屏体验 -> 原 SPA 架构瓶颈 -> Next 多渲染模式适配。

### 可背答案

> 当时不是为了追新框架，而是业务进入增长阶段后，公开内容页、数据详情页和 Blog 对自然流量很重要。原来的 Umi 更适合 SPA 和中后台，很多核心内容依赖客户端渲染，动态 metadata、canonical、sitemap、结构化内容这些 SEO 能力做起来成本比较高。  
>   
> Next.js 的价值在于可以按页面选择 SSR、SSG、ISR 或 CSR。公开 SEO 页面可以服务端输出稳定 HTML，登录后的复杂应用继续保持客户端交互。再加上我们后续对页面定制化、性能和缓存策略要求更高，所以最终决定渐进式迁移。

## 4. Next.js 是否有 BFF 层

### 你的回答问题

- 你说“没有 BFF，只做 middleware 中转”，比较诚实。
- 但要补清楚 BFF 和 middleware 的区别，否则容易显得概念模糊。

### 正确思路

BFF 是面向前端业务聚合/裁剪/编排数据；middleware 更偏请求前置处理、鉴权、重写、跳转、header/cookie 处理。

### 可背答案

> 我们项目里 Next.js 主要价值是 SSR 和 SEO 页面，并没有做很重的 BFF 聚合层。BFF 通常会做接口聚合、字段裁剪、服务端鉴权、业务编排，把多个后端接口整理成前端更好消费的数据。  
>   
> 我们更多是用 middleware 或服务端能力做一些请求中转、cookie/header 处理、鉴权前置和 SSR 数据获取。这个要区分开，不能把所有服务端逻辑都叫 BFF。

## 5. 代码仓库学习助手怎么做

### 你的回答问题

- 你讲出了 Git 仓库拉取、静态分析、结构化报告、聊天 Agent 和文件引用，方向是好的。
- 但要更清楚地区分“固定分析流程”和“Agent 工具调用流程”。

### 正确思路

项目可以拆成 ingestion、index、analysis、chat 四层。

### 可背答案

> 这个项目我会拆成四层。第一层是仓库接入，用户输入 Git 地址后拉取代码，并做目录、语言、依赖和关键文件识别。第二层是索引层，把文件路径、README、package、路由、核心模块等结构化出来。第三层是分析层，用大模型生成项目结构报告，比如技术栈、模块职责、核心流程和可能的设计模式。第四层是聊天 Agent，用户可以围绕项目提问，Agent 通过读文件、搜索代码、查看目录等工具找到上下文，再生成回答，并引用具体文件作为依据。

## 6. Workflow 还是 Agent 自动决策

### 你的回答问题

- 你提到 LangGraph + 工具调用是对的。
- 但“工作流”和“Agent”之间要讲清楚：不是完全二选一，可以是工作流控制阶段，Agent 在阶段内决策。

### 正确思路
