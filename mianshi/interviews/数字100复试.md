# 数字100复试面经

面试日期：2026-05-07  
岗位方向：AI 前端 / 工程效率 / Agent 工作流  
题型特点：AI 工具对比、Skill 设计、确定性、AI 工程思考

## 本轮考点

- AI 编程工具定位：Cursor、Claude Code、Codex 的差异和使用边界
- Skill 设计：边界、流程、输入输出、约束和维护
- Skill 确定性：结构化输入、固定流程、模板化输出、校验门禁
- Skill 编排：主 Skill、子 Skill、上下文传递和最终收敛
- AI 工程思考：产品形态、研发方式、组织能力和工程师价值

## 总体复盘

这轮问题明显偏 AI 工程方法论，不是单纯问你会不会用工具，而是看你是否能把 AI 工具、Skill 和工程流程联系起来。  

核心考察点有四类：

- 你是否真的理解 Cursor、Claude Code、Codex 这类工具的定位差异。
- 你是否能设计出可复用的 Skill，而不是只写 prompt。
- 你是否知道如何提高 Skill 输出的确定性。
- 你是否对 AI 工程化、协作方式和未来岗位形态有自己的判断。

回答策略：

- 工具题不要只比模型，要比交互形态、上下文范围、工程执行能力。
- Skill 题不要只讲格式，要讲边界、流程、输入输出和约束。
- 确定性题要讲结构化输入、固定流程、模板、校验和门禁。
- AI 思考题不要空泛，最好落到工程、组织和产品三个层面。

## 1. 你用过 Cursor、Claude Code、Codex 等工具，觉得它们之间有什么区别

### 关键考点

- 你是否把这些工具当成不同定位的工程工具，而不是“谁更强”的排行榜。
- 你是否理解它们的交互方式、上下文组织和适用任务差异。
- 你是否能讲出团队落地时的使用边界。

### 短答

我不会简单说哪个工具绝对更好，而是会按场景区分：Cursor 更像 IDE 内的开发助手，Claude Code 和 Codex 更偏 agent 型 coding tool，适合更长链路的工程任务。

### 详细分析

这类工具可以从四个维度看：

**第一维：交互形态**

- Cursor：更像 IDE 内置 AI，适合边写边改。
- Claude Code / Codex：更像任务执行型 agent，适合围绕目标推进。

**第二维：上下文范围**

- Cursor 更强在当前文件和编辑器上下文。
- Claude Code / Codex 更强调代码库级别理解和任务上下文连续性。

**第三维：任务粒度**

- Cursor 适合高频、小步、局部开发任务。
- Claude Code / Codex 更适合跨文件修改、重构、排查、验证。

**第四维：工程化程度**

- Cursor 更偏个人开发效率。
- Claude Code / Codex 更容易进入需求拆解、批量修改、测试补全、Review 辅助等流程型场景。

### 实操口径

项目里我会按任务粒度选择工具，而不是固定押一个工具。日常写组件、改局部逻辑、补类型时，我更倾向用 Cursor 贴着 IDE 做小步修改；如果是跨文件排查、重构、补测试、跑命令验证，我会用 Claude Code / Codex 这类 agent 型工具，让它先读目录和约束，再小步提交 diff。团队落地时，我会把工具使用写进研发流程：哪些任务适合 AI 草拟，哪些核心链路必须人工 Review，最后用 TypeScript、Lint、测试和构建结果做验收。

### 可背答案

> 我不会简单说哪个工具绝对更强，而是按使用场景区分。Cursor 更像 IDE 内的一体化 AI 编程助手，适合边写边补全、局部修改和多文件联动，进入开发流很自然。Claude Code 和 Codex 这类工具，我会更偏向理解成 agent 型 coding tool，它们更适合围绕明确目标去执行任务，比如读代码库、跨文件修改、跑命令、验证结果和总结改动。  
>   
> 对我来说，它们的核心区别不只是模型，而是交互方式、上下文范围和工程执行能力。Cursor 更适合高频、小步、编辑器内联的开发；Claude Code 和 Codex 更适合复杂任务、代码库理解和流程型工作。

### 注意点

- 不要答成“某某最强，其他都不行”。
- 不要只讲模型能力，不讲产品形态和工程流程。
- 最好从“个人效率”和“团队流程”两个角度都讲一下。

### 可能追问

- 你会在什么场景优先用 Cursor？
- Claude Code / Codex 更适合哪些任务？
- 如果让团队统一落地，你会怎么分配使用边界？

## 2. 怎么写好一个 Skill

### 关键考点

- 你是否理解 Skill 不是一段长 prompt，而是一套可复用的任务规范。
- 你是否知道 Skill 设计要关注输入、边界、步骤、输出和异常处理。
- 你是否能从工程资产角度看 Skill。

### 短答

写好一个 Skill，核心不是写得长，而是让它有清晰边界、稳定流程、明确输入输出和可复用约束。

### 详细分析

一个好的 Skill，通常要满足五点：

**第一，任务边界清晰**

- 它解决什么问题
- 不解决什么问题
- 在什么场景下触发

**第二，流程稳定**

- 先做什么
- 再做什么
- 遇到特殊情况怎么办

**第三，输入输出明确**

- 输入需要什么上下文
- 输出应该长什么样
- 是否要求固定格式

**第四，约束充分**

- 使用哪些工具
- 遵循哪些规范
- 哪些动作不能做

**第五，可维护**

- 不要写成大而全百科
- 尽量模块化
- 能和模板、脚本、参考资料配合

### 实操口径

我会先从一个高频、边界清楚的任务开始写 Skill，比如这次的 `interview-notes`。先定义触发场景和不触发场景，再写输入要求、输出结构、执行流程和质量检查。真正落地时，我不会把所有知识都塞进 Skill，而是让 Skill 只保留流程和判断规则，详细模板或参考资料放在项目文件里。这样后续换 Cursor、Claude Code 或 Codex，也能按同一套项目级 Skill 执行。

### 可背答案

> 我理解 Skill 不是一段很长的 prompt，而是一套可复用的任务规范。写好一个 Skill，关键是让它的任务边界清晰、执行流程稳定、输入输出明确、工具和约束充分，同时又能长期维护。  
>   
> 具体来说，我会先定义这个 Skill 解决什么问题、不解决什么问题，再写清楚执行步骤、输出格式、工具使用规则和异常处理方式。这样 Skill 才不是一次性问答，而是能反复复用的工程资产。

### 注意点

- 不要把 Skill 写成“全能说明书”。
- 不要只有原则，没有步骤。
- 最好强调可复用和可维护。

### 可能追问

- Skill 和普通 prompt 的区别是什么？
- Skill 适合解决什么问题，不适合解决什么问题？
- 你会怎么维护 Skill 的版本演进？

## 3. 怎么保证 Skill 的产出是确定的

### 关键考点

- 你是否知道大模型天然有随机性，确定性需要通过工程手段增强。
- 你是否能讲出从输入、流程、输出、校验四层提高确定性的办法。
- 你是否能把 Skill 和模板、schema、测试联系起来。

### 短答

Skill 的确定性不是靠一句“请稳定输出”实现的，而是靠结构化输入、固定流程、模板化输出、自动校验和质量门禁共同保证。

### 详细分析

提高 Skill 产出确定性，常见做法有四层：

**第一层：输入标准化**

- 提供固定上下文
- 输入字段结构化
- 避免模糊描述

**第二层：流程固定化**

- Skill 内部步骤顺序固定
- 明确先分析、再执行、再验证
- 特殊情况有兜底规则

**第三层：输出模板化**

- 固定章节
- 固定字段
- 固定 JSON / Markdown / 表格格式

**第四层：校验与门禁**

- schema 校验
- 规则检查
- 测试 / 构建 / Review
- 对关键结果做人审或二次校验

你可以加一句很工程的话：

> 大模型输出不可能天然完全确定，所以真正追求的是“可控确定性”，也就是在给定输入和约束下，结果波动尽量小、格式尽量稳、关键步骤可验证。

### 实操口径

我会把确定性拆成“输入确定、流程确定、输出确定、验收确定”。比如面经 Skill 里，输入必须包含公司、轮次和题目；流程固定为读取索引、生成面经、识别考点、更新 README；输出固定为关键考点、短答、详细分析、实操口径、可背答案、注意点、可能追问；验收则检查是否有 `本轮考点`、是否区分做过和会做、是否没有编造指标。这样即使不同 AI 工具执行，产物也会保持相对稳定。

### 可背答案

> Skill 的确定性不能只靠提示词本身，而是要靠工程化手段增强。我一般会从四层做：第一，输入标准化，把上下文和参数结构化；第二，流程固定化，Skill 内部步骤顺序明确；第三，输出模板化，要求固定字段和固定格式；第四，增加校验和门禁，比如 schema 校验、规则检查、测试、构建和人工 Review。  
>   
> 我的理解是，大模型不可能天然完全确定，所以真正要追求的是“可控确定性”，也就是在相同输入和规则下，让结果波动尽量小、输出结构尽量稳定、关键产物可验证。

### 注意点

- 不要说“temperature 调低就行”，这太浅。
- 一定要讲模板、校验和门禁。
- 最好强调“可控确定性”，而不是绝对确定性。

### 可能追问

- Skill 和普通 prompt 相比，为什么更容易稳定？
- 如果输出还是波动大，你先改哪里？
- 你会怎么给 Skill 做验收？

## 4. Skill 中调用其他 Skill 怎么做

### 关键考点

- 你是否理解 Skill 的组合关系，而不是每个 Skill 都独立孤立。
- 你是否知道 Skill 之间调用要注意边界和上下文污染。
- 你是否能讲出编排而不是“互相套娃”。

### 短答

Skill 调用其他 Skill，本质上是能力编排，不是无限嵌套。关键是职责拆分清楚、输入输出约定统一、上下文传递可控。

### 详细分析

Skill 组合一般有三种方式：

**第一种：主 Skill 编排子 Skill**

- 主 Skill 负责整体流程
- 子 Skill 负责单一能力

比如：

- 主 Skill：生成面经
- 子 Skill：提炼问题、压缩答案、生成速记清单

**第二种：顺序流水线**

- 一个 Skill 输出结构化结果
- 下一个 Skill 接着消费结果

**第三种：按条件分发**

- 根据任务类型选择不同子 Skill

要注意三件事：

1. 不要让 Skill 互相无限依赖。
2. 子 Skill 输入输出必须标准化。
3. 主 Skill 要做最终校验和收敛。

### 实操口径

我会把 Skill 组合做成“主流程 + 专项能力”的关系。比如面经沉淀可以由主 Skill 负责解析公司轮次、更新文件和索引；如果后续有更细的子 Skill，可以分别负责“React 考点归类”“AI Agent 题实操化”“可背答案压缩”。子 Skill 只返回结构化结果，最后仍由主 Skill 统一检查格式、项目口径和 README 路由，避免多个 Skill 各自输出导致上下文膨胀和风格不一致。

### 可背答案

> Skill 调用其他 Skill，我会把它理解成能力编排，而不是简单嵌套。通常是主 Skill 负责整体流程和最终收敛，子 Skill 负责单一能力，比如提炼、改写、校验、生成模板等。  
>   
> 做这种组合时，关键是职责拆分清楚、输入输出约定统一、上下文传递可控，同时避免 Skill 之间无限依赖。我的习惯是让主 Skill 做最终校验，这样组合之后产出仍然可控。

### 注意点

- 不要讲成“一个 Skill 里直接塞所有 Skill”。
- 一定要强调标准化输入输出。
- 最后收敛责任要明确。

### 可能追问

- Skill 组合过多时，怎么避免上下文膨胀？
- 如何避免主 Skill 和子 Skill 职责重叠？
- 子 Skill 输出不稳定时怎么办？

## 5. 你对 AI 有哪些思考

### 关键考点

- 你是否对 AI 有自己的工程和产品视角，而不只是技术热情。
- 你是否能平衡机会、风险和组织变化。
- 你是否能把 AI 思考落到自己岗位价值上。

### 短答

我对 AI 的核心看法是：它最大的价值不只是“更会回答问题”，而是把软件从静态功能系统，逐步变成能理解目标、调用工具、持续执行任务的系统。

### 详细分析

我通常会从三个层面看 AI：

**第一层：产品形态变化**

- 从传统 GUI 走向 GUI + LUI 混合
- 用户不只是点按钮，而是直接描述目标
- 软件从“功能集合”变成“任务完成系统”

**第二层：工程方式变化**

- AI 会显著改变研发流程
- Prompt、Skill、Agent、RAG、工具调用会变成新的工程基础设施
- 前端工程师不只是写界面，还要理解状态协议、工具协议和任务流

**第三层：组织与能力变化**

- 未来工程师的价值，不只是写代码速度
- 更重要的是：定义边界、约束系统、沉淀资产、做质量控制
- 会用 AI 的人不一定有优势，但能把 AI 变成团队稳定生产力的人会很有优势

如果落回你自己：

- 你更关注 AI 前端、Agent 体验、Vibe Coding 和工程化结合
- 你不觉得 AI 会直接替代工程师，而是会抬高对抽象、产品理解和系统设计的要求

### 实操口径

我会把这个思考落到具体工作里：做 AI 产品时，前端不只是渲染对话框，而是要处理流式输出、工具调用状态、长任务反馈、错误兜底和可观测；做 AI 提效时，也不是随手问模型，而是把 Prompt、Skill、Checklist、代码模板和 Review 规则沉淀成团队资产。像当前项目里的 `interview-notes` Skill，就是把“面经整理”从一次性聊天变成可复用流程的例子。

### 可背答案

> 我对 AI 的一个核心看法是，它最大的价值不只是更会生成内容，而是让软件开始具备“围绕目标持续执行任务”的能力。对产品来说，这意味着交互方式会从传统 GUI 逐步走向 GUI 和自然语言协同；对工程来说，这意味着 Prompt、Skill、Agent、RAG、工具调用和可观测性会变成新的基础设施。  
>   
> 我也不觉得 AI 会简单替代工程师，反而会抬高对工程师的要求。未来更有价值的人，不只是写代码快，而是能把 AI 能力做成稳定、可控、可复用的系统，能定义边界、沉淀资产、控制质量，并把工具真正融入团队流程。

### 注意点

- 不要答得太空泛，比如“AI 很厉害，未来很好”。
- 不要极端说“AI 会完全替代前端”。
- 最好把思考落到产品、工程、组织三个层面。

### 可能追问

- 你觉得 AI 会不会替代前端工程师？
- AI 时代前端工程师最核心的竞争力是什么？
- 你为什么会对 Agent 和 Skill 这类方向感兴趣？
