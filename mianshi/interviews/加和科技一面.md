# 加和科技一面面经

面试日期：2026-04-29  
岗位方向：AI 前端 / React / Next.js 前端  
题型特点：对话式 Agent、可观测性、多媒体能力、Agent 指标体系

## 本轮考点

- 超长上下文 Agent：渲染性能、上下文可视化、交互体验、成本稳定性
- 前端可观测：错误、性能、业务链路、日志关联
- 浏览器录制方案：getUserMedia、MediaRecorder、上传和兼容性
- Agent 指标体系：性能、稳定性、质量、成本、工具链路、业务指标
- AI 全栈工程师：交互层、编排层、数据层、工程稳定性
- 从 0 到 1 项目架构：业务约束、技术选型、模块分层、质量体系
- 大型项目 Vibe Coding：规范先行、Prompt/Skill 资产、质量门禁、风险分级

## 总体复盘

这轮问题明显偏 AI 前端和 Agent 工程化，不是单纯问大模型概念，而是追前端在真实产品里的职责边界。核心在于三件事：

- 超长上下文和对话式 Agent，前端如何保证性能和体验。
- 可观测性是否做过，是否能讲清采集什么、怎么上报、怎么定位问题。
- 语音录制、Agent 指标这些能力，是否能从链路视角拆清楚。

回答策略：

- Agent 题不要只讲模型，要讲前端的渲染、交互、状态、可观测和成本提示。
- 可观测题不要只说接 Sentry，要讲错误、性能、业务链路和日志关联。
- 录制题不要只说 `getUserMedia`，要讲录制、编码、上传、异常、权限。

## 1. 超长上下文，对话式 Agent 前端能做的优化有哪些

### 关键考点

- 你是否理解长对话的瓶颈不只是模型慢，还有前端渲染和交互问题。
- 你是否能从性能、上下文管理、体验、成本可视化四个层面回答。
- 你是否知道前端和后端在上下文裁剪上的职责边界。

### 短答

超长上下文的对话式 Agent，前端优化重点是四类：渲染性能、上下文可视化、交互体验、成本与稳定性。

### 详细分析

超长上下文下，前端常见问题有：

1. 消息越来越多，DOM 节点和 Markdown 渲染开销暴涨。
2. 流式输出频繁更新，导致 React 不断重渲染。
3. 用户看不清当前上下文到底带了什么，容易迷失。
4. 首字延迟、整段响应耗时、上下文长度接近上限时，用户没有感知。

前端可以做的优化主要有四层：

**第一层：渲染性能**

- 虚拟列表，只渲染可视区消息。
- 流式更新节流，不要每个 token 都触发 render。
- 只增量更新最后一条消息，历史消息完成后冻结。
- Markdown、代码高亮、公式渲染做缓存。
- 长消息折叠，代码块和引用块按需展开。

**第二层：上下文管理可视化**

- 展示历史轮数、引用片段、知识来源、工具调用记录。
- 旧消息折叠，只展开当前任务链路。
- 支持历史按需加载，而不是一次把所有消息都渲染出来。
- 如果有摘要压缩或上下文裁剪，前端最好有可见提示。

**第三层：交互体验**

- 自动滚动只在用户停留底部时启用。
- 用户上滑看历史时，不强行拉回底部。
- 提供引用跳转、消息定位、分段摘要、重新生成、停止生成。
- 把“消息流”和“任务流”区分展示，尤其是工具调用型 Agent。

**第四层：成本与稳定性**

- 展示 token 消耗、上下文长度预警。
- 记录首字时间、完整返回时间、流中断率。
- 区分模型慢、网络慢、前端卡顿。
- 监控长会话下的渲染耗时、错误率、重试次数。

前后端职责边界也要说清楚：

- 真正的上下文裁剪策略通常由 Agent 编排层或后端控制。
- 前端负责把上下文状态可视化、把超长会话交互做顺畅、把成本和异常暴露出来。

### 实操口径

如果项目里真做长对话 Agent，我会先从最后一条流式消息下手，避免每个 token 都触发整棵消息列表重渲染：流式内容做节流合并，历史消息完成后缓存 Markdown 渲染结果；消息列表用虚拟列表或按需加载；长代码块、引用和工具结果默认折叠。交互上会处理“用户看历史时不自动滚到底部”，并记录首字时间、完整响应时间和前端渲染耗时，方便区分模型慢还是前端卡。

### 可背答案

> 超长上下文的对话式 Agent，前端优化我会重点做四件事。第一是渲染优化，比如虚拟列表、流式更新节流、只增量更新最后一条消息、Markdown 和代码块缓存，避免长对话反复全量渲染。第二是上下文可视化，把历史轮数、引用内容、知识来源、工具调用记录展示出来，并支持折叠旧消息和按需加载历史，降低阅读负担。第三是交互优化，比如自动滚动与手动滚动分离、引用跳转、长消息折叠、停止生成、重新生成和任务状态提示，让用户知道 Agent 当前在做什么。第四是成本与稳定性，包括 token 长度提示、上下文上限预警、响应耗时、流中断重试和异常监控。  
>   
> 我理解这个问题的核心不是单纯让页面别卡，而是让超长对话在性能、可理解性和可控性上都能成立。

### 注意点

- 不要只说“虚拟列表”，这会显得只懂一点渲染优化。
- 不要把上下文裁剪全部说成前端做，容易越界。
- 不要忽略流式输出导致的高频 render 问题。

### 可能追问

- 如果历史消息必须全部可见，虚拟列表怎么做？
- 前端能不能参与上下文裁剪？
- 如何判断是模型慢还是前端渲染慢？

## 2. 有没有做过可观测，怎么做的

### 关键考点

- 你是否真的做过可观测，而不是只装过一个 SDK。
- 你是否能把错误、性能、日志、业务链路拆开讲。
- 你是否知道“采集什么”和“如何定位问题”同样重要。

### 短答

可观测不只是错误上报，而是把错误、性能、用户行为、核心链路状态和上下文日志串起来，支持发现问题、定位问题和评估影响。

### 详细分析

前端可观测通常分四层：

**第一层：错误可观测**

- JS 运行时错误：`window.onerror`
- Promise 未捕获：`unhandledrejection`
- 资源加载错误：script、img、css
- React 错误边界

**第二层：性能可观测**

- Core Web Vitals：LCP、INP、CLS
- FCP、TTFB、长任务
- 首字返回时间、完整响应时间
- 关键接口耗时、失败率、重试率

**第三层：业务链路可观测**

- 登录、支付、提交、生成、发布等关键链路埋点
- 每个环节的成功率、耗时、失败原因
- Agent 场景下的提问次数、回答中断、重试、工具调用失败

**第四层：日志与定位能力**

- traceId / requestId 串联前后端日志
- 记录用户环境：页面 URL、浏览器、设备、网络、地区
- 记录页面状态：用户操作、当前会话、关键参数
- 关键流程带 stage 状态，便于定位到底卡在哪一段

如果结合你自己的项目经验，可以这样映射：

- FastMoss：接入 Clarity 与性能监控 SDK，做异常上报和飞书报警。
- AI / Agent 场景：补充首字时间、整段回答时间、流中断、重试率、工具失败率等指标。

### 实操口径

我会先把监控分成基础错误和业务链路两类接入。基础层用 `error`、`unhandledrejection`、资源加载错误和 React ErrorBoundary 兜住异常；性能层采集 LCP、INP、CLS、长任务和接口耗时；Agent 链路再补自定义埋点，比如发送问题、首字返回、流式完成、中断、重试、工具调用开始/成功/失败。上报时带 traceId、会话 id、页面 URL、模型/工具类型，方便前后端日志串起来定位。

### 可背答案

> 我理解的可观测不是简单接一个错误监控 SDK，而是把错误、性能、日志和业务链路串起来。错误层会采集 JS 运行时错误、Promise 未捕获、资源加载失败和错误边界；性能层会采集 LCP、INP、CLS、长任务、接口耗时；业务层会重点看登录、支付、生成、发布等关键链路的成功率和耗时；日志层会通过 traceId、页面上下文、用户环境把前后端问题串起来。  
>   
> 对 AI / Agent 场景，我会额外关注首字返回时间、完整回复时间、流中断率、重试率和工具调用失败率，这样才能区分是模型慢、网络慢，还是前端渲染和状态管理出了问题。

### 注意点

- 不要把“埋点”和“可观测”混为一谈，埋点只是其中一部分。
- 不要只讲错误监控，性能和关键链路同样重要。
- 最好强调日志关联和问题定位，而不是只说“上报了很多数据”。

### 可能追问

- 你们怎么做报警，怎么避免噪声太多？
- 如何区分接口问题、模型问题和前端问题？
- 做过白屏监控吗？

## 3. 要实现录制，有什么方案

### 关键考点

- 你是否掌握浏览器录音 / 录屏能力的基本方案。
- 你是否会从权限、格式、上传、兼容性和异常处理角度回答。
- 你是否知道不同场景对应不同技术方案。

### 短答

要实现录制，常见方案是基于 `getUserMedia` 获取音视频流，再结合 `MediaRecorder` 做录音或录屏；如果要求更高，可以接 WebRTC、Web Audio API 或原生能力。

### 详细分析

要先分场景：

**场景一：纯录音**

- 用 `navigator.mediaDevices.getUserMedia({ audio: true })`
- 用 `MediaRecorder` 分段录制音频
- 录完得到 Blob，再上传服务端

**场景二：录屏**

- 用 `navigator.mediaDevices.getDisplayMedia()`
- 结合 `MediaRecorder` 录制屏幕流

**场景三：音视频同时录制**

- `getUserMedia({ video: true, audio: true })`
- 统一交给 `MediaRecorder`

如果需求更复杂，比如：

- 实时语音识别
- 降噪
- 波形展示
- 分片上传
- 边录边传

则会进一步用到：

- Web Audio API 做音频处理
- WebSocket / WebRTC 做实时传输
- 分片上传和断点续传

前端实现时要考虑：

- 麦克风 / 屏幕权限申请和失败提示
- 编码格式，如 `webm`、`mp4`、`wav`
- 录制时长限制
- 暂停 / 继续 / 停止
- 上传失败重试
- 不同浏览器兼容性

### 实操口径

如果项目里要做录制，我会先确认是录音、录屏还是音视频一起录。纯录音先用 `getUserMedia` 拿音频流，`MediaRecorder` 分片收集 Blob；如果需要边录边传，就按固定时间片上传，服务端做合并或实时识别。前端状态会拆成 idle、permission、recording、paused、uploading、success、failed，并处理权限拒绝、设备不可用、超过时长、上传失败重试和用户中途取消。

### 可背答案

> 如果是浏览器里做录制，我会先按场景拆。纯录音通常用 `getUserMedia` 获取音频流，再配合 `MediaRecorder` 录制成 Blob 上传；录屏一般用 `getDisplayMedia`；如果是音视频一起录，也可以统一交给 `MediaRecorder`。  
>   
> 如果需求更复杂，比如实时转写、边录边传、降噪、波形展示，我会再结合 Web Audio API、分片上传、WebSocket 或 WebRTC。前端侧除了录制本身，还要处理权限申请、格式兼容、暂停继续、时长限制、上传重试和异常提示。

### 注意点

- 不要只说 `MediaRecorder`，要先讲获取媒体流的入口。
- 要先问清楚是录音、录屏还是音视频一起录。
- Safari、移动端浏览器的兼容性最好顺手提一句。

### 可能追问

- 如果要边录边传怎么做？
- 如果要做实时语音转文字怎么办？
- 录屏和录音的权限处理有什么差异？

## 4. Agent 需要监测的指标有哪些

### 关键考点

- 你是否能把 Agent 指标拆成性能、质量、稳定性、业务价值几个层次。
- 你是否知道前端能采集什么、后端 / Agent 层又该采集什么。
- 你是否理解 Agent 不只是“回答快不快”，还要看成功率、工具执行、用户体验和成本。

### 短答

Agent 的指标不能只看响应时间，至少要看性能指标、稳定性指标、质量指标、工具调用指标、成本指标和业务指标。

### 详细分析

Agent 场景建议从六类指标看：

**第一类：性能指标**

- 首字返回时间
- 完整回答时间
- 工具调用耗时
- 页面渲染耗时
- 长对话滚动与更新卡顿情况

**第二类：稳定性指标**

- 流中断率
- 请求失败率
- 工具调用失败率
- 重试率
- 超时率

**第三类：质量指标**

- 用户是否继续追问
- 回答是否被重新生成
- 工具调用结果是否被用户接受
- 用户反馈 like / dislike
- 任务完成率

**第四类：上下文与成本指标**

- token 输入输出量
- 上下文长度
- 会话轮数
- 每次回答成本
- 超长上下文压缩频率

**第五类：工具与链路指标**

- 每类工具调用次数
- 工具成功率
- 工具平均耗时
- 哪一步最容易失败
- 是否存在重复调用和无效调用

**第六类：业务指标**

- 用户留存
- 提问频率
- 任务完成率
- 转化率
- 日活 / 周活中的 Agent 使用占比

如果从前端视角讲，可以重点强调能采集到的：

- 首字时间、完整返回时间
- 中断、重试、停止生成
- 页面渲染与滚动性能
- 用户行为反馈

### 实操口径

我会把 Agent 指标埋到状态机里，而不是散落在 UI 事件里。比如一次对话从 submit、request_start、first_token、tool_call_start、tool_call_end、stream_end 到 user_feedback 都有事件点。前端负责采集体验相关指标：首字时间、完整耗时、中断、停止生成、重试、渲染卡顿和用户反馈；后端和编排层负责模型耗时、工具耗时、token、成本和工具失败原因。这样排查时能看到问题卡在模型、工具、网络还是前端渲染。

### 可背答案

> Agent 需要监测的指标不能只看响应时间，我一般会分六类。第一类是性能指标，比如首字返回时间、完整回答时间、工具调用耗时和页面渲染耗时；第二类是稳定性指标，比如流中断率、失败率、超时率和重试率；第三类是质量指标，比如任务完成率、重新生成率、用户反馈和继续追问率；第四类是上下文和成本指标，比如 token 输入输出量、上下文长度、会话轮数和单次成本；第五类是工具链路指标，比如工具调用次数、成功率和失败阶段；第六类是业务指标，比如留存、使用频率和转化。  
>   
> 从前端角度，我会特别关注首字时间、完整回答时间、中断重试、渲染卡顿和用户交互行为，因为这些最能反映真实体验，也最容易帮助我们区分是模型问题、工具问题还是前端性能问题。

### 注意点

- 不要只讲技术指标，业务指标也要提。
- 不要把“模型指标”和“前端可观测指标”完全混在一起。
- 最好强调“前端重点看体验和链路状态，后端重点看模型和工具执行”。

### 可能追问

- 如何定义 Agent 的“成功率”？
- 工具调用失败率高时，你怎么定位？
- 前端怎么区分是流中断还是模型返回慢？

## 5. 你对 AI 全栈工程师有什么看法

### 关键考点

- 你是否理解 AI 全栈工程师不只是“前端 + 调模型 API”。
- 你是否能站在工程视角看 AI 产品，而不是只看模型能力。
- 你是否知道自己当前能力边界，以及未来如何往 AI 全栈靠近。

### 短答

我理解的 AI 全栈工程师，不是单纯会前端、后端和调用模型，而是能围绕 AI 产品的完整链路交付价值，包括交互层、编排层、数据层、可观测性和成本控制。

### 详细分析

这个问题本质上不是让你定义一个新岗位，而是看你对 AI 工程化的理解是否完整。  

我理解 AI 全栈工程师至少要覆盖五层能力：

**第一层：产品与交互层**

- 对话体验
- 流式输出
- 工具调用结果展示
- 长任务反馈
- 多模态交互

**第二层：应用编排层**

- Prompt 设计
- RAG 接入
- Agent 工作流
- 工具调用协议
- 状态机和任务编排

**第三层：服务与数据层**

- 后端接口
- 鉴权
- 会话存储
- 向量检索
- 文件处理
- 任务队列

**第四层：工程与稳定性**

- 可观测
- 成本控制
- 缓存
- 限流
- 灰度
- 回滚

**第五层：模型与业务结合能力**

- 不是只会接模型，而是知道什么时候该用模型、什么时候该靠规则和工程手段解决。
- 能根据业务目标权衡准确率、延迟、成本和体验。

如果你想把回答落回自己身上，可以这样表达：

- 你现在的强项在前端交互、Agent 体验、流式输出、任务状态、可观测和工程化。
- 你也在补后端接口、RAG、向量检索、工具编排和成本控制。
- 你认为 AI 全栈不是一天变成的，而是从“AI 前端工程师”逐步往“AI 产品全链路工程师”演进。

### 实操口径

我会把 AI 全栈理解落到“能不能交付一个稳定 AI 产品”上。前端这边我能负责流式体验、工具结果展示、长任务状态、错误兜底和可观测；往后端和编排层，我会关注会话存储、RAG 检索、工具协议、任务队列、限流和成本控制。面试里我不会说自己已经覆盖所有层，而是强调我现在以 AI 前端和工程化为强项，正在往 Agent 编排和数据检索能力补齐。

### 可背答案

> 我理解的 AI 全栈工程师，不是简单把前端、后端和模型 API 拼在一起，而是能围绕 AI 产品的完整链路交付价值。往上要理解用户交互和产品体验，比如流式输出、长任务反馈、工具调用结果展示；往中间要能做 Prompt、RAG、Agent 编排和工具接入；往下要能处理接口、鉴权、存储、检索、任务队列和可观测；同时还要关注成本、稳定性和灰度发布。  
>   
> 我自己的理解是，AI 全栈的核心不在于“会不会调模型”，而在于能不能把模型能力做成稳定、可用、可观测、可持续优化的产品。我现在更强的是前端交互、Agent 体验和工程化这部分，也在持续补后端编排、检索和成本控制能力。

### 注意点

- 不要把 AI 全栈理解成“什么都沾一点”，那样会显得很虚。
- 不要只讲模型，真正加分的是工程化和产品化能力。
- 最好能结合你自己的能力边界说，不要把自己吹成已经全覆盖。

### 可能追问

- 你觉得自己离 AI 全栈还差哪一块？
- AI 前端工程师和 AI 全栈工程师最大的区别是什么？
- 你觉得未来前端会不会被 AI 全栈取代？

## 6. 从 0 到 1 设计一个中型项目，需要考虑哪些事情

### 关键考点

- 你是否能从业务目标出发做架构设计，而不是先堆技术栈。
- 你是否具备中型项目的工程视角，包括多人协作、质量、性能和演进。
- 你是否能讲清“现在先做什么、以后怎么扩展”。

### 短答

从 0 到 1 设计一个中型项目，我会先看业务目标和约束，再做技术选型、模块分层、工程规范、性能安全和可演进性设计。

### 详细分析

中型项目设计不能一上来就说 React、Next.js、Node，而要先回答“这个项目解决什么问题”。  

我通常会从六层考虑：

**第一层：业务与约束**

- 是官网、后台、SaaS、AI 工具还是数据平台。
- 是否需要 SEO、SSR、多语言、多地区、支付、权限。
- 团队规模、交付周期、上线频率、维护周期。

**第二层：技术选型**

- React / Next.js / Vite 的选择依据。
- 状态管理方案。
- 请求层、表单方案、组件体系。
- 是否需要 Monorepo、BFF、服务端渲染。

**第三层：模块分层**

- 页面层
- 业务模块层
- 通用组件层
- 请求层
- 状态层
- 工具层

目标是让职责边界清晰，后续迭代不会越来越乱。

**第四层：工程与质量**

- TypeScript、ESLint、Prettier、提交规范。
- CI/CD、测试、Code Review。
- 环境区分：开发、测试、预发、生产。

**第五层：性能与安全**

- 首屏性能、拆包、懒加载、图片和字体优化。
- 鉴权、权限、接口签名、敏感信息保护。
- 错误监控、性能监控、日志和埋点。

**第六层：可演进性**

- 未来模块扩展是否容易。
- 业务增长后是否需要拆分。
- 公共能力是否可以沉淀。

如果你想让回答更像负责人视角，可以补一句：

> 好的项目架构不是一开始设计得很复杂，而是在当前业务阶段不过度设计，同时为后续扩展和多人协作留下清晰边界。

### 实操口径

如果真从 0 到 1 做中型项目，我会先拉一版架构决策文档，写清业务形态、技术选型理由、目录结构、请求层、状态管理、权限模型和发布流程。第一周先把脚手架、Lint、TypeScript、基础组件、请求封装、环境配置和 CI 跑通；核心业务链路出来后再补监控埋点和测试。这样不是一开始追求大而全，而是先把团队协作和后续扩展的底座打稳。

### 可背答案

> 如果让我从 0 到 1 设计一个中型项目，我不会先选框架，而是先明确业务目标和约束，比如它是后台系统、AI 工具还是 SaaS 平台，是否需要 SEO、SSR、多语言、支付和权限，以及团队规模和交付节奏。  
>   
> 在这个基础上，我再做技术选型和分层设计，比如确定 React 还是 Next.js、状态管理怎么做、请求层怎么封装、组件体系和目录结构怎么拆。然后会同步补齐工程规范、类型约束、测试、CI/CD、监控埋点和性能优化，确保项目不是只跑起来，而是能长期维护和迭代。  
>   
> 我理解中型项目的重点不是技术堆得多，而是边界清晰、协作顺畅、质量可控、后续可演进。

### 注意点

- 不要只讲技术栈，面试官更想看你有没有架构顺序感。
- 不要一上来就过度设计，容易显得脱离业务。
- 最好把“业务目标 -> 技术选型 -> 工程治理 -> 可演进性”串成一条线。

### 可能追问

- 为什么这个场景你会选 Next.js / React / Vite？
- 中型项目和大型项目的架构思路区别是什么？
- 从 0 到 1 时哪些规范你会一开始就上，哪些会后补？

## 7. 从 0 开始 Vibe Coding 一个大型项目，有哪些需要注意的点

### 关键考点

- 你是否理解大型项目里 AI 提效的边界和风险。
- 你是否知道从 0 开始用 Vibe Coding，不只是写代码，还要沉淀规范、模板和质量门禁。
- 你是否具备“让 AI 进入团队流程”的意识，而不是停留在个人使用工具。

### 短答

从 0 开始用 Vibe Coding 做大型项目，重点不是让 AI 先把代码写出来，而是先定义规范、边界、资产沉淀和质量门禁，再让 AI 参与需求拆解、实现、测试和 Review。

### 详细分析

大型项目里，Vibe Coding 最大的风险不是“AI 写得不够快”，而是：

- 输出风格不一致
- 重复造轮子
- 违反项目边界
- 核心链路质量不可控
- 团队每个人各自问各自的，知识无法沉淀

所以从 0 开始做，我会优先搭四层基础：

**第一层：项目约束先行**

- 目录结构
- 模块边界
- 组件规范
- 请求层规范
- 状态管理规范
- 错误处理规范

AI 只有在规则明确时，输出才会稳定。

**第二层：Prompt 和 Skill 资产化**

- 需求拆解模板
- 组件生成模板
- 测试生成模板
- Code Review 模板
- Bug 排查模板
- 项目专属 Skill

这样 AI 才不会每次“从零发挥”。

**第三层：工程门禁**

- TypeScript
- ESLint
- 单测 / E2E
- 构建检查
- 人工 Review

AI 可以写代码，但不能跳过质量体系。

**第四层：风险分级**

- 样板代码、文档、脚手架、测试适合优先让 AI 参与。
- 支付、权限、登录、SSR、核心数据链路要更保守。
- 核心链路的 AI 输出必须人工把关。

如果面试官想听“大型项目”的特殊性，你可以强调：

- 大型项目最大的问题不是写一个功能，而是长期一致性。
- Vibe Coding 真正有价值的地方，是把团队经验变成 Prompt、Skill、Checklist 和模板，而不是个人临场发挥。

### 实操口径

如果从 0 开始 Vibe Coding 大型项目，我会先让 AI 参与“搭框架和写规范”，而不是直接铺业务代码。先产出目录结构、模块边界、组件模板、请求模板、错误处理模板和 Review 清单，再让 AI 按这些模板生成局部代码。每个 AI 任务都要求小步 diff，并说明改了哪些文件、为什么改、怎么验证。核心链路比如登录、权限、支付、SSR 只允许 AI 做分析和草稿，最终必须人工 Review 和测试通过。

### 可背答案

> 如果从 0 开始用 Vibe Coding 做一个大型项目，我不会先让 AI 直接铺代码，而是会先把项目的目录结构、模块边界、组件规范、请求层、状态管理和错误处理这些基础约束定下来。因为大型项目最怕的不是写得慢，而是风格不一致、边界混乱、重复造轮子和核心链路质量失控。  
>   
> 在这个基础上，我会把高频任务沉淀成 Prompt 模板、Skill、Checklist 和代码模板，比如需求拆解、组件生成、测试补全、Code Review、Bug 排查。然后再通过 TypeScript、Lint、测试、构建和人工 Review 做质量门禁。  
>   
> 我的理解是，大型项目里 Vibe Coding 的重点不是“AI 写了多少代码”，而是“AI 是否被纳入了一套稳定、可复用、可审查的工程体系”。

### 注意点

- 不要把 Vibe Coding 讲成“AI 自动写完整项目”，这会显得不专业。
- 不要忽略团队协作和一致性，这才是大型项目最核心的问题。
- 重点要落在规范、模板、Skill、Review、门禁，而不是单次提效。

- 如果团队里每个人都各自问 AI，会有什么问题？
- 你会优先把哪些东西沉淀成 Skill？
- 大型项目里哪些模块适合 AI 深度参与，哪些不适合？
