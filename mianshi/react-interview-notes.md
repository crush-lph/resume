# React 为主的前端面试经验整理

这份文档聚焦 `React` 为主的前端面试准备，目标不是只背散题，而是帮助你按真实面试链路复习：`原理`、`项目`、`优化`、`表达`。

## 1. React 面试最常考的 6 大模块

### 1.1 Hooks

高频点：

- `useState` 的更新机制
- `useEffect` 的执行时机、清理函数、依赖数组
- `useRef` 与 `useState` 的区别
- `useMemo` / `useCallback` 的适用场景
- 闭包陷阱与 stale closure
- 自定义 Hook 的封装思路

常见追问：

- `useEffect` 为什么会重复执行？
- 为什么依赖项写错会引发死循环？
- `useRef` 为什么修改后不触发渲染？
- `useMemo` 是不是一定能提升性能？

准备建议：

- 每个 Hook 都准备一段“作用 + 原理 + 踩坑 + 项目例子”。
- 不要只会解释 API，要能说明“什么时候不该用”。

### 1.2 渲染与更新机制

高频点：

- React 更新流程
- 虚拟 DOM 的作用
- diff 策略
- 同层比较的原因
- `key` 的作用
- Fiber 架构解决了什么问题
- React 18 的并发特性

常见追问：

- 从一次 `setState` 到页面更新经历了什么？
- React diff 为什么不是完整树比较？
- 为什么不能随便用数组下标当 `key`？
- Fiber 和传统递归 diff 的核心区别是什么？

准备建议：

- 至少能口述一次“状态更新 -> 调度 -> 协调 -> 提交”的流程。
- React 18 不一定要讲到源码，但要能说清并发更新在解决什么问题。

### 1.3 组件设计

高频点：

- 受控组件与非受控组件
- 状态提升
- props drilling
- `Context` 的适用范围
- `forwardRef`
- `memo`
- 高阶组件、Render Props、Hook 的对比

常见追问：

- 表单为什么常用受控组件？
- 组件设计中，状态应该放在哪里？
- 什么时候适合拆“容器组件”和“展示组件”？
- 如何设计一个可复用的业务组件？

准备建议：

- 面试官常通过这部分判断你的工程感觉，而不只是 API 熟悉度。
- 最好准备一个你自己做过的组件封装案例。

### 1.4 性能优化

高频点：

- 父组件更新引发的子组件重渲染
- `React.memo` 的使用边界
- 大列表优化
- 虚拟列表
- 路由懒加载
- 代码分割
- 图片与资源加载优化
- 渲染性能排查

常见追问：

- 页面卡顿时你怎么定位？
- 为什么加了 `memo` 还是会重复渲染？
- 大表单、大列表页面你怎么优化？
- 你做过哪些真实有效的性能优化？

准备建议：

- 不要只说“加了 memo、做了懒加载”。
- 要讲清楚：`问题现象`、`排查方式`、`优化动作`、`最终结果`。

### 1.5 React 生态与工程化

高频点：

- `React Router`
- 状态管理：`Redux`、`Context`、`Zustand`
- SSR / CSR / SSG 的区别
- `Webpack` / `Vite`
- 错误监控、埋点、发布流程
- 接口请求管理与缓存策略

常见追问：

- 什么时候该用 Redux，什么时候 Context 就够了？
- Vite 为什么比 Webpack 冷启动更快？
- React 项目里怎么做异常监控？
- 大型项目如何管理全局状态和异步请求？

准备建议：

- 如果你项目中没有完整用过所有生态，不要硬背细节。
- 重点讲你实际碰过的选型和取舍。

### 1.6 项目深挖

高频点：

- 组件拆分思路
- 状态设计
- 接口管理
- 权限控制
- 性能瓶颈
- 线上问题定位
- 技术选型依据

常见追问：

- 你做过最复杂的 React 项目是什么？
- 其中最难的问题是什么，你怎么解决的？
- 如果让你重做一次，你会怎么优化？
- 你在项目里的核心贡献是什么？

准备建议：

- 真实面试里，这部分权重常常比八股更高。
- 至少准备 `2` 个可以深挖的 React 项目。

## 3. 真实面试中的回答重点

### 3.1 回答原理题

建议用这个结构：

1. 先说定义
2. 再说机制
3. 再说使用场景
4. 最后补一个项目里的例子

例如回答 `useRef` 时，不要只说“它可以保存一个值”，还要补上：

- 它返回的是一个可变对象
- `.current` 的变化不会触发组件重渲染
- 常用于 DOM 引用、跨渲染周期保存值、避免闭包问题

### 3.2 回答性能优化题

建议用这个结构：

1. 问题现象
2. 定位过程
3. 优化方案
4. 数据结果

例如：

- 某个列表页滚动卡顿
- 通过 React DevTools Profiler 发现重复渲染严重
- 使用虚拟列表并减少不必要 props 变化
- 首屏渲染时间和交互流畅度明显改善

### 3.3 回答项目题

建议用这个结构：

1. 项目背景
2. 你负责的部分
3. 技术难点
4. 解决方案
5. 最终结果
6. 复盘与改进

### 8.2 审核后可直接采用的结论

#### 事件循环

可以保留的核心说法：

- JavaScript 通过任务队列协调同步代码、异步回调和 UI 渲染
- 同步代码先执行
- 微任务会在当前宏任务结束后优先清空
- 浏览器通常会在一次任务和微任务处理完成后安排渲染

需要修正：

- 如果语境是“浏览器事件循环”，不要把 `process.nextTick` 当成浏览器微任务示例
- 更稳的浏览器微任务例子是 `Promise.then`、`queueMicrotask`、`MutationObserver`

面试更稳的表达：

- 浏览器里常见宏任务有整体脚本、定时器、I/O 回调、消息事件
- 常见微任务有 `Promise.then`、`queueMicrotask`、`MutationObserver`
- 如果微任务持续产生新的微任务，确实可能导致渲染被长期推迟，从而出现页面卡顿

#### Promise 和 `Promise.all`

这部分整体是正确的，可以直接保留：

- Promise 有 `pending`、`fulfilled`、`rejected` 三种状态
- `Promise.all` 全部成功才成功，任一失败就立即 reject
- 手写实现时要处理非 Promise 输入，并保证结果顺序与输入顺序一致

补充一个容易漏掉的点：

- 空数组传给 `Promise.all([])` 时应直接 resolve 一个空数组

#### SSE 与 WebSocket

主结论基本正确，可以保留：

- SSE 是服务端到客户端的单向流式传输
- WebSocket 是全双工通信
- AI 聊天里的“服务端持续输出文本”场景通常更适合 SSE

需要修正为更稳的说法：

- SSE 本质上是基于 HTTP 的文本事件流，不是原生二进制协议
- 如果要传二进制，通常是额外编码后传输，不是 SSE 的核心优势
- “SSE 在 HTTP/2 下性能极佳”可以说成“在很多场景下表现更好、连接复用更友好”，不要说得过满

#### Flex 与 Grid

整体可保留：

- Flex 更适合一维布局
- Grid 更适合二维布局
- 导航、对齐、行内分配常用 Flex
- 仪表盘、页面骨架、多列区域编排常用 Grid

需要收敛的说法：

- “Grid 在处理复杂嵌套时能减少 DOM 层级”不是必然，只能说“有时可以减少额外包裹层”

#### Token 与上下文窗口

大方向对，但有一句要修正：

- Token 是模型处理文本的计量单位，这点正确
- API 计费、上下文窗口限制、响应时延与 Token 数量相关，这点正确

需要修正：

- “超过长度会导致丢失记忆”不够准确
- 更稳的说法是：超过上下文窗口时，旧内容需要被截断，或者请求会失败，模型并不是像人一样“失忆”

#### 深拷贝

整体正确，可以保留：

- 递归处理对象和数组
- 使用 `WeakMap` 处理循环引用
- 特殊类型要单独处理，如 `Date`、`RegExp`、`Map`、`Set`
- `JSON.parse(JSON.stringify())` 会丢失函数、`undefined`、`Symbol`、正则、日期等信息

补充一个更稳的点：

- 面试里最好顺带说明是否需要保留原型链、属性描述符和不可枚举属性，这能拉开深度差距

#### React Fiber

题目方向对，但原文里有一个关键说法要改：

- Fiber 解决的是 React 在大规模更新下主线程长时间被占用、交互响应差的问题
- 它把渲染工作拆成更细粒度的工作单元，并允许调度与中断
- 它强调的是“可中断、可恢复、可按优先级调度”

需要修正：

- 不要说“Fiber 将渲染过程拆分为可中断的微任务”
- 更准确的说法是“拆分为可调度的工作单元，由调度器协调执行”
- 微任务会在一次循环内尽快清空，本身不适合表达 Fiber 的可中断调度模型

#### 流式文本渲染优化

这部分很实战，建议保留：

- 不要每来一个 token 就触发一次 React 更新
- 可以批量聚合后再更新，例如按时间片或按帧刷新
- 只更新最后一个消息气泡，避免整段消息列表反复 diff
- 历史对话很长时要结合虚拟列表
- Markdown、代码高亮、滚动到底等逻辑都要做节流

补充一个更稳的表达：

- 如果流式内容中包含 Markdown 代码块，优先做“分段解析”或“稳定块再高亮”，不要每个字符都全量重新解析

#### Prompt 管理

整体正确，值得保留：

- Prompt 应模板化
- 要支持变量注入
- 要有版本管理
- 开发时最好能预览最终发给模型的完整 Prompt

补充两个更工程化的点：

- 前端只负责可视化配置和调试体验，真正的安全边界仍应落在后端
- 敏感字段注入要区分“展示态”和“发送态”，避免把机密信息泄漏到日志或前端缓存

#### RAG 前端展示

这部分整体方向正确，可以保留：

- 前端要处理引用标注、来源预览、中间状态展示、用户反馈闭环
- 流式输出时要保证引用编号和正文内容稳定对齐

补充一个常见考点：

- 需要考虑引用源为空、引用失效、重复引用合并、跨段落引用跳转这些 UI 细节

#### Web Worker

整体正确，可以保留：

- 适合把重计算从主线程挪走
- 可用于文本清洗、分块、简单向量计算、复杂流数据解析
- 不应该在 Worker 中操作 DOM

补充一个更稳的点：

- 频繁 `postMessage` 的序列化成本可能很高，大对象要考虑 `Transferable` 或共享内存方案

#### Markdown、公式和代码高亮

整体很靠谱，可以保留：

- Markdown 解析库配合插件系统
- 数学公式可用 `KaTeX` 或 `MathJax`
- 代码高亮可用 Prism、lowlight、rehype 体系
- 富文本渲染必须做 XSS 防护

补充一个更稳的点：

- 如果内容来自模型输出，不能只依赖 Markdown 库本身，仍应做 HTML 白名单或 `DOMPurify` 清洗

#### Vite 预构建

整体正确，可以保留：

- 开发时基于浏览器原生 ESM 按需加载
- 依赖预构建主要用 `esbuild`
- HMR 快
- 生产构建仍依赖 Rollup 生态完成更成熟的打包优化

#### Prompt Injection 防护

方向对，但必须修正“防护边界”：

- 前端可以做输入提示、风险标记、展示层隔离和输出消毒
- 但 Prompt Injection 的核心防线不能只靠前端
- 真正关键的是后端策略、工具权限隔离、系统提示保护、模型输出校验、审计日志

面试更稳的表达：

- 前端是第一层体验防线，不是唯一安全边界
- 如果只说“前端过滤敏感词”会显得安全理解偏浅

#### AI Agent、桌面端架构和综合题

这些题可以保留，适合中高级面试：

- 企业级 AI Chat 桌面端选型
- AI Agent 对前端开发模式的影响
- 如何评估 AI 前端组件库质量
- 过去项目中的技术难题复盘

答题建议：

- 少讲概念口号，多讲边界、取舍和失败案例
- 尤其是 `Electron vs Tauri`、`本地存储设计`、`模型 Provider 抽象`、`权限控制`、`错误恢复`
